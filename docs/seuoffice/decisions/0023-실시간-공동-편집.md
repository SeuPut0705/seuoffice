# 0023 실시간 공동 편집: 가운데 서버 하나와 공통 클라이언트 하나

- 날짜: 2026-11-10
- 상태: 확정. 첫 판을 냈고 시험 단계다(2026-11-11). 형식 넷을 한 판에 냈다(아래 8번과 다르게 한 까닭은 `작업기록.tsv`의 collab-unlogged 행)
- 결정한 사람: 스풋("중앙화된 도구로 제작해서 적용해보자"). 모양은 메인 세션이 설계안 두 개를 견주어 정했다
- 결정 0008의 1번("실시간 공동 편집은 하지 않는다")을 뒤집는다. 0008의 잠금 흐름은 어댑터가 없는 형식에 그대로 남는다

## 맥락

결정 0008은 실시간 공동 편집을 하지 않기로 했다. 근거 가운데 둘이 틀렸거나 달라졌다.

- "다섯 모델 모두 연산 층이 없다"는 확인 없이 쓴 말이었다. 다시 조사하니 이렇다.

  | 형식 | 편집 한 건의 모양                                                                          | 순서 있는 연산 흐름    |
  | ---- | ------------------------------------------------------------------------------------------ | ---------------------- |
  | docx | ProseMirror 트랜잭션(TipTap 3.31.0). 본문 밖 상태(구역, 머리글, 스타일, 메모)는 React 상태 | 본문은 있음            |
  | xlsx | Univer 뮤테이션. 한 곳(`App.tsx`의 `CommandExecuted`)에서 모두 보인다                      | 있음(좌표가 위치 기준) |
  | pptx | `pptx-ops`의 직렬화되는 Op. 데스크톱은 이미 순번 붙은 기록을 남긴다                        | 있음                   |
  | pdf  | `edit-ops`의 Op와 순수 리듀서                                                              | 있음                   |
  | hwp  | wasm 호출을 감싼 클로저, 위치는 엔진 인덱스                                                | 없음                   |

- "서버가 없다"는 붙이는 쪽(유유)이 AWS에 서버를 올리므로 막는 까닭이 아니다.

스풋이 형식마다 따로 만들지 말고 한 도구로 만들라고 했다.

## 결정

1. **가운데 서버가 순서를 정한다.** 문서마다 빈틈없는 변경 기록 하나를 둔다. 변경은 보낸 쪽이 최신 판을 보고 만든 것일 때만 붙는다(`base === head`). 서버는 변경 내용을 읽지 않는다. 형식별 코드가 서버에 없다.
2. **밀린 쪽이 자기 변경을 다시 맞춘다.** 동시에 보낸 둘 가운데 하나가 먼저 붙고, 다른 쪽은 앞선 변경을 받아 자기 미확정 편집을 그 위로 옮긴 뒤 다시 보낸다. 옮기는 방법만 편집기마다 다르고, 그 한 함수(`integrate`)가 어댑터다.
3. **같은 변경은 두 번 붙지 않는다.** `(client, seq)`가 기록 안에서 하나뿐이다. 응답을 잃고 다시 보내도, 끊긴 연결의 요청이 늦게 닿아도 결과가 같다.
4. **기준 파일은 서버가 들고 있다.** 편집 묶음(epoch) 하나는 기준 파일 하나와 그 위의 변경 기록이다. 늦게 들어온 사람은 기준 파일을 열고 기록을 처음부터 따라간다. 저장한 파일을 다시 열어 이어 가는 방식은 쓰지 않는다(저장 → 다시 열기가 같은 상태를 준다는 보장이 시트에서 깨진다).
5. **저장은 한 판의 내보내기다.** 입력을 잠깐 멈추고, 자기 편집이 모두 확정되면 남의 변경을 붙잡아 둔 채 파일을 만든다. 그 파일은 정확히 한 판의 내용이다. 붙이는 쪽은 판 번호가 더 클 때만 덮어쓴다.
6. **어긋나면 멈춘다.** 클라이언트들이 같은 판에서 문서 지문을 서버에 보내고, 다르면 모두 읽기 전용이 된다. 조용히 틀린 파일이 저장되는 것보다 멈추는 쪽을 고른다.
7. **붙이는 쪽이 연결을 가진다.** 주소와 토큰은 붙이는 쪽 페이지에 있고 편집기 iframe에는 들어가지 않는다(AI 중계, 결정 0009와 같은 방식).
8. **형식은 하나씩 붙인다.** 어댑터가 없는 형식과 `collab` 옵션 없이 연 문서는 지금과 똑같이 돈다. 한글은 연산 흐름이 없어 잠금으로 둔다.

묶음은 `@seuoffice/collab` 하나다(`/client`, `/server`, `/conformance`). 서버는 저장소 포트(`CollabStore`)와 메모리 구현만 싣는다. 오래 가는 저장소는 붙이는 쪽이 자기 DB에 맞춰 구현한다.

## 버린 대안

두 설계안을 따로 만들게 하고 독립 판정을 받았다(합계 21 대 20, 판정도 아래 까닭으로 같은 쪽).

- **서버가 합쳐지는 공유 모델(Yjs)을 들고 있는 방식.** 밀려서 다시 보내는 일이 없고 시트의 행 삽입 충돌이 자연스럽게 풀린다. 버린 까닭: 문서 편집기의 되돌리기를 갈아 끼워야 해서 변경 추적과 표 처리의 가드(`history$`)가 깨진다. 서버가 문서마다 모델을 메모리에 들어 한 프로세스로 몰아야 한다. 충돌에서 누가 이기는지가 서버 도착 순서가 아니다. 다섯 편집기 상태를 모두 식별자 공간으로 다시 써야 첫 형식이 나온다.
  - 이 안에서 가져온 것: 기준 파일을 서버가 보관, 클라이언트 id를 서버가 발급, 부작용 없는 `produceFile`, 위치가 안 맞는 연산은 어댑터 안에서 식별자로 주소 잡기.
- **서버가 연산을 변환(OT).** 서버가 다섯 형식의 코드를 실어야 하고 편집기를 고칠 때마다 서버도 배포해야 한다.
- **저장한 파일을 체크포인트로.** 위 4번의 까닭.
- **형식마다 따로 구현.** 스풋이 한 도구로 하라고 했다. 재시도·재접속·저장 멈춤을 다섯 번 만들게 된다.

## 결과

- 상위 파일 수정은 편집기마다 붙이는 자리 한 곳과, 어댑터가 필요로 하는 손잡이다. 얼마인지는 형식을 붙일 때 `upstream-edits.md`에 적는다.
- 프로토콜의 순서·중복 없음은 모델 검사(`formal/collab-protocol/`)와 무작위 네트워크 시험으로 확인한다. 편집기별 수렴은 어댑터마다 적합성 시험으로 확인한다. 둘은 다른 보증이다.
- 저장하는 사람은 저장 동안 입력이 잠깐 멈춘다. 동시에 많이 치면 느린 쪽이 여러 번 밀릴 수 있다. 재지 않았다.
- 붙이는 쪽 할 일이 0008과 달라진다: WebSocket 서버 운영, 접속 인증, `CollabStore` 구현, 판 번호 조건부 저장.
