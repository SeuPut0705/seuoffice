# 0008 제품 이름, 배포 플랫폼, 업데이트 채널

- 날짜: 2026-11-09
- 상태: 확정
- 결정한 사람: 이름과 채널은 메인 세션 판단(스풋 변경 가능), 배포 플랫폼은 스풋

## 맥락

Apache-2.0은 상위 제품 이름(GenOffice, IeumOffice, 이음오피스)을 쓸 권리를 주지 않는다(라이선스 6절, NOTICE). seuoffice 설치 파일과 창에 그 이름이 남으면 안 된다. 0002는 내부 이름을 그대로 두고 사용자에게 보이는 이름만 바꾸기로 했다. 0007은 저장소를 공개하고, 유유헬스케어에는 판 확인을 거친 안정 판 채널을 따로 주기로 했다.

들여온 셸에는 사용자가 설정 → 정보에서 고르는 업데이트 채널(안정 버전, 베타 버전)이 있었다. 베타는 GitHub 프리릴리스를 따라갔다.

## 결정

### 배포 플랫폼

- 앱 릴리스는 **Apple Silicon Mac(arm64)**과 **Windows(x64)** 두 가지만 낸다. 스풋이 정했다. Linux, Intel Mac(x64, universal), ARM Windows는 빌드도 릴리스도 하지 않는다.
- 릴리스 설정은 새 파일 `apps/shell/electron-builder.seuoffice.cjs`다. 상위 `electron-builder.cjs`를 불러 그 위에 대상만 좁힌다: Mac은 dmg와 자동 업데이트용 zip(arm64), Windows는 NSIS(x64). Linux 설정(`linux`, `deb`, `rpm`)은 빼고, 묶기 직전(`beforePack`)에 다른 플랫폼·CPU가 오면 멈춘다. 상위 스위치 `GENOFFICE_MAC_X64=1`, `GENOFFICE_WIN_ARM64=1`도 거부한다.
- 릴리스 빌드만 `--config electron-builder.seuoffice.cjs`로 이 설정을 쓴다. 그냥 `electron-builder`나 `npm run dist:*`는 상위 설정 그대로라 개발 빌드는 바뀌지 않는다.

### 제품 이름

- 사용자에게 보이는 이름은 모든 언어에서 `seuoffice`다. 한국어 화면도 `seuoffice`를 보인다. 아직 한국어 상표 이름이 없기 때문이다. 정하면 `packages/i18n/src/product.ts`의 `LOCALIZED_PRODUCT_NAMES`에 한 줄 더하면 된다.
- 설치본 이름: `productName`과 `description`(NSIS 설치 파일의 FileDescription) `seuoffice`, `appId`(Mac 번들 ID) `com.seuput.seuoffice`, 실행 파일 `seuoffice.exe`·`seuoffice.app`, 설치 파일 `seuoffice-Setup-<판>.exe`·`seuoffice-<판>-arm64.dmg`. 상위 설정의 리눅스 패키지 이름도 `seuoffice`로 바꿨지만 릴리스하지 않는다.
- 창과 문서 제목(`apps/*/src/renderer/*.html`)도 `seuoffice`로 시작한다.
- 업데이트·이슈·저장소 주소는 `SeuPut0705/seuoffice`다.
- Windows 파일 연결 ProgId(`seuoffice.WordDocument` 등)와 레지스트리 키 `Software\seuoffice`는 제품 이름을 따른다. 이음오피스와 한 PC에 같이 깔려도 서로의 등록을 건드리지 않는다.
- 내부 이름(`@genoffice/*`, `GENOFFICE_*`, `genoffice` 명령, `~/.genoffice`)은 0002대로 둔다. 이음오피스가 붙인 명령 이름 `ieumoffice`, `~/.ieumoffice`, MCP 서버 이름 `ieumoffice-editor`도 이번에는 두었다. 사용자가 터미널과 AI 도구 설정에 적는 이름이라 바꾸려면 따로 정해야 한다(아래 결과).
- `USER_DATA_DIR_NAME`은 `productName`을 따르므로 사용자 데이터 폴더도 `seuoffice`가 된다. seuoffice 설치본이 아직 하나도 없으니 옮길 데이터가 없다.
- 제품 정체성 시험(`apps/shell/tests/product-identity.test.ts`)이 새 이름을 고정하고, 창 제목과 설치본 이름에 `GenOffice`, `IeumOffice`, `이음오피스`가 없는지 확인한다.

### 업데이트 채널

설치본은 GitHub `SeuPut0705/seuoffice`의 릴리스에서 업데이트를 받는다(electron-updater, GitHub 공급자). 채널은 둘이다.

| 채널     | 누가 쓰나    | Windows 설치 파일                 | Mac 설치·업데이트 파일                                                   | 피드 파일                      | 무엇을 받나                          |
| -------- | ------------ | --------------------------------- | ------------------------------------------------------------------------ | ------------------------------ | ------------------------------------ |
| `latest` | 일반 사용자  | `seuoffice-Setup-<판>.exe`        | `seuoffice-<판>-arm64.dmg`, `seuoffice-<판>-arm64-mac.zip`               | `latest.yml`, `latest-mac.yml` | 새로 낸 릴리스 전부(프리릴리스 포함) |
| `stable` | 유유헬스케어 | `seuoffice-Setup-<판>-stable.exe` | `seuoffice-<판>-arm64-stable.dmg`, `seuoffice-<판>-arm64-mac-stable.zip` | `stable.yml`, `stable-mac.yml` | GitHub가 "Latest"로 표시한 릴리스만  |

두 플랫폼이 같은 방식으로 채널을 정한다.

- **채널은 빌드할 때 정한다.** 사용자가 바꾸는 설정이 아니다. 묶을 때 환경 변수 `SEUOFFICE_UPDATE_CHANNEL`(`latest` 기본, `stable`)을 주면 `electron-builder.cjs`가 `publish.channel`에 넣는다. electron-builder는 그 채널 이름으로 피드 파일을 만들고 `resources/app-update.yml`에 `channel:`을 적는다. 앱은 켤 때 그 파일을 읽어(`src/main/update-build-channel.ts`) 채널을 정한다. 파일을 읽지 못하거나 `latest`가 아니면 `stable`로 본다. 확인한 판만 받는 쪽이 안전하기 때문이다.
- 설정 → 정보의 "업데이트 채널" 선택 칸과 그 IPC, 저장 값, 도움말 줄을 지웠다. 이 값을 바꿔도 다른 채널 설치 파일로 갈아타지 않기 때문에, 남겨 두면 사용자를 속이는 선택 칸이 된다.
- `stable` 설치본이 받는 설치 파일도 `stable` 빌드다. 업데이트를 받아도 채널이 바뀌지 않는다.
- 릴리스 하나에 두 플랫폼, 두 채널을 함께 붙인다. 태그 `vX.Y.Z`를 올리면 `.github/workflows/seuoffice-release.yml`이 Windows(windows-latest)와 Mac(macos-latest, arm64 러너)에서 각각 두 번 묶어(일반, `stable`) 그 태그로 **프리릴리스**를 만들고 열네 파일(Windows 설치 파일 둘과 `.blockmap` 둘, `latest.yml`, `stable.yml`, Mac dmg 둘, zip 둘과 `.blockmap` 둘, `latest-mac.yml`, `stable-mac.yml`)을 붙인다. 이때부터 일반 사용자는 받고 유유는 받지 않는다.
- **안정 판으로 올리기(promote).** 스풋이 그 판을 확인한 뒤 손으로 한다.

  ```bash
  gh release edit vX.Y.Z --prerelease=false --latest
  ```

  GitHub가 그 릴리스를 "Latest"로 표시하면 `stable` 설치본이 다음 확인(켤 때 15초 뒤, 그 뒤 4시간마다)에서 받는다. 워크플로는 이 일을 하지 않는다.

- 자동 생성 릴리스 본문은 앱 업데이트 창에 그대로 보인다. 올리기 전에 본문을 사용자용 글로 고친다.

### 서명

- **Windows.** 저장소 secrets `WIN_CSC_LINK`(PFX의 base64 또는 https 주소)와 `WIN_CSC_KEY_PASSWORD`가 있으면 electron-builder 기본 signtool 서명으로 앱 실행 파일, 언인스톨러, 설치 파일, 함께 묶는 `.exe`(xlsx-sidecar, win-ocr)에 서명한다. 상위의 `GENOFFICE_WIN_SIGN_MODE` 훅은 `scripts/win-sign.cjs`를 부르는데, 이 저장소(이음오피스 포함)에는 그 스크립트가 없다. 그래서 그 훅을 쓰지 않는다. 서명했으면 설치 파일 둘, 앱 실행 파일, sidecar의 서명 상태가 모두 `Valid`여야 하고, 안 했으면 모두 `NotSigned`여야 한다. 반쯤 서명된 빌드는 실패한다.
- **Mac.** electron-builder 표준 이름 `CSC_LINK`(Developer ID Application 인증서 .p12의 base64)와 `CSC_KEY_PASSWORD`, 공증용 `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`(상위 `build/notarize-dmg.js`가 이미 읽는 이름)를 쓴다. `CSC_LINK`가 있으면 `electron-builder.seuoffice.cjs`가 Developer ID로 서명하고 hardened runtime을 켜고 앱을 공증한다. dmg는 `notarize-dmg.js`가 공증하고 staple한다. 인증서만 있고 공증 자격이 빠지면 묶기 전에 멈춘다. Gatekeeper가 공증 안 된 Developer ID 앱을 막기 때문이다. `CSC_LINK`가 없으면 상위처럼 임시(ad hoc) 서명이다. 워크플로는 서명했으면 `Developer ID Application` 서명, `spctl` 통과, dmg staple을 확인하고, 안 했으면 `Signature=adhoc`을 확인한다.
- **서명 없는 빌드는 릴리스하지 않는다.** 한 플랫폼이라도 비밀값이 없으면 그 빌드는 시험용 워크플로 결과물(`seuoffice-windows-x64`, `seuoffice-mac-arm64`)로만 남고, 릴리스 작업은 어떤 릴리스도 건드리기 전에 멈춘다. 서명된 판이 한 번 나가면 그 뒤 업데이트는 같은 서명자만 받으므로(`docs/releasing.ko.md`), 처음 공개하는 판부터 두 플랫폼 모두 서명해야 한다.

### 사람이 할 일(Apple과 Windows 서명 준비)

코드로 대신할 수 없다. 스풋이 한다.

1. Apple Developer Program 가입(연 99달러, 개인 또는 조직). 팀 ID(`APPLE_TEAM_ID`)를 확인한다.
2. Developer ID Application 인증서를 만든다(Xcode 또는 developer.apple.com → Certificates). 키체인에서 개인 키와 함께 .p12로 내보내고 암호를 정한다.
3. 공증용 자격: appleid.apple.com에서 앱 암호(app-specific password)를 만든다.
4. 저장소 secrets 등록(값은 커밋·로그에 남기지 않는다):

   ```bash
   base64 -i DeveloperID.p12 | gh secret set CSC_LINK --repo SeuPut0705/seuoffice
   gh secret set CSC_KEY_PASSWORD --repo SeuPut0705/seuoffice
   gh secret set APPLE_ID --repo SeuPut0705/seuoffice
   gh secret set APPLE_APP_SPECIFIC_PASSWORD --repo SeuPut0705/seuoffice
   gh secret set APPLE_TEAM_ID --repo SeuPut0705/seuoffice
   ```

5. Windows 코드 서명 인증서(OV/EV 또는 Azure Trusted Signing)를 구해 PFX를 `WIN_CSC_LINK`, 암호를 `WIN_CSC_KEY_PASSWORD`로 등록한다. 하드웨어 토큰에만 들어 있는 EV 인증서는 PFX로 꺼낼 수 없으니 그때는 서명 방식을 따로 정한다.
6. 비밀값을 넣은 뒤 `workflow_dispatch`로 한 번 돌려 두 결과물이 서명·공증되었는지 보고, 그다음 첫 태그를 올린다.

## 버린 대안

- **사용자 설정 채널 유지(안정/베타 선택 칸).** 유유 PC에서 누군가 베타로 바꾸면 확인하지 않은 판이 들어간다. 채널은 배포하는 쪽이 정해야 한다.
- **채널별 저장소나 릴리스 분리.** 저장소를 둘로 나누면 릴리스와 태그를 두 곳에서 관리해야 한다. 한 릴리스에 두 빌드를 붙이고 GitHub "Latest" 표시로 승격하는 편이 손이 적다.
- **semver 프리릴리스 태그(`v1.2.0-stable.1`)로 채널 구분.** electron-updater의 GitHub 공급자는 사용자 정의 채널 이름을 태그에서 읽을 때 `alpha`/`beta` 말고는 제대로 다루지 않고, 승격할 때 판 번호를 바꿔 다시 빌드해야 한다.
- **한국어 이름을 새로 지어 넣기.** 상표 검토 없이 이름을 정하지 않는다.

## 결과

- 이음오피스 설치본과 seuoffice 설치본은 한 PC에 함께 깔리고, 서로의 파일 연결·데이터 폴더·업데이트를 건드리지 않는다.
- 상위 설정의 Linux·Intel Mac 대상과 상위 워크플로(`windows-build.yml`, `mac-build.yml`, `linux-build.yml`)는 그대로 두었다. seuoffice 릴리스는 `seuoffice-release.yml`만 낸다. 상위 워크플로는 손으로 돌릴 때만 동작하고(`workflow_dispatch`, 상위 파일을 고친 PR) 이음오피스 이름으로 검사하므로 seuoffice에서는 실패한다. 지울지는 따로 정한다.
- 명령 이름 `ieumoffice`와 `~/.ieumoffice`, MCP 서버 이름 `ieumoffice-editor`, 도움말 본문 속 상위 이름(`GenOffice`는 화면에서 제품 이름으로 바뀐다)은 남아 있다. 명령 이름을 바꿀지는 따로 정한다.
- 상위 문서 `docs/releasing.ko.md`는 이음오피스 절차다. seuoffice 절차는 이 결정과 워크플로 머리 주석이 대신한다.
