# 0020 main 푸시마다 미리보기 판

- 날짜: 2026-11-09
- 상태: 확정, "main 푸시마다 판을 낸다"는 [0027](0027-판은-모아서-낸다.md)이 바꿈(판은 모아서 사람이 시작한다)
- 결정한 사람: 스풋(방향과 "한꺼번에 진행"), 방식은 메인 세션

## 맥락

v0.12.12를 낼 때 커밋이 설치본에 닿기까지 이렇게 걸렸다(실행 기록으로 잼).

| 단계                       | 시간                                                        |
| -------------------------- | ----------------------------------------------------------- |
| 푸시 뒤 CI 녹색까지 기다림 | 약 31분(CI 42579086298)                                     |
| 사람이 태그를 닮           | 사람이 볼 때까지                                            |
| 앱 빌드와 릴리스           | 약 11~12분(실행 42595497496: mac 8.5분, windows 10.5분)     |
| 사람이 안정 채널로 올림    | 사람이 볼 때까지                                            |
| 설치본이 알아챔            | 켤 때 또는 최대 4시간(`updater.ts`의 `RECHECK_INTERVAL_MS`) |

헤르메스 에이전트를 살펴보니 같은 문제를 채널로 푼다. 데스크톱 묶음은 electron-updater로 판째 받고, canary 채널이 자주 판을 받으며, stable은 확인한 판만 받는다(`/tmp/hermes-research`의 `hermes_cli/update_channel.py`).

## 결정

- **main 푸시마다 판을 낸다.** `.github/workflows/seuoffice-desktop.yml`이 main 푸시에 돈다(문서만 바꾼 푸시는 뺀다: `**/*.md`, `docs/**`). 판 번호는 저장소의 가장 높은 `v*` 태그에 patch를 하나 더한 것이다. `apps/shell/package.json` 판이 더 높으면 그 판을 쓴다(이음을 따라잡아 판이 오른 경우). 빌드 때만 `package.json`에 판을 적고 저장소에는 커밋하지 않는다.
- **CI와 함께 돌고, 둘 다 녹색일 때만 낸다.** 빌드는 CI를 기다리지 않고 바로 시작한다. 릴리스 작업이 같은 커밋의 `CI`(ci.yml)와 `seuoffice`(seuoffice.yml) 실행을 기다려, 둘 다 성공해야 미리보기 판(pre-release)을 만든다. 하나라도 실패하면 아무것도 내지 않는다. CI를 다시 돌려 녹색이 되면 이 릴리스 작업만 다시 돌리면 된다.
- **안정 채널은 지금처럼 사람이 올린다.** 일반(latest) 채널 설치본은 새 판을 바로 받는다. 유유가 쓰는 안정(stable) 채널은 스풋이 확인하고 `gh release edit vX.Y.Z --prerelease=false --latest`로 올린 판만 받는다. README 다운로드 단추도 안정 판을 받는다.
- **미리보기 판은 최근 10개만 둔다.** 그보다 오래된 미리보기 판은 릴리스와 태그를 지운다. 안정 판은 지우지 않는다.
- **앱은 1시간마다 확인한다.** `apps/shell/src/main/updater.ts`의 `RECHECK_INTERVAL_MS`를 4시간에서 1시간으로 줄였다. GitHub 릴리스 피드(Atom)를 읽는 것이라 API 한도와 무관하다.
- **빌드에서 셸을 두 번 만들지 않는다.** 묶기 첫 단계가 `npm run dist:*`로 셸을 다시 빌드했는데, 바로 앞 `npm run build:all`이 이미 빌드했다. 첫 단계도 고지 파일만 만들고 `electron-builder`를 바로 부른다.

## 버린 대안

- **stable 묶음을 다시 만들지 않고 latest 묶음을 재사용(`--prepackaged`).** 플랫폼마다 1~1.5분을 줄일 수 있어 보였다. 하지만 electron-builder는 이미 묶은 앱을 받으면 앱을 묶는 단계를 건너뛰고, 업데이트 채널은 그 단계에서 앱 안 `resources/app-update.yml`에 적힌다. 그대로 쓰면 안정 채널 설치본이 일반 채널 판을 받는다. 파일을 고치면 Mac은 서명을 다시 해야 한다. 얻는 시간에 비해 위험이 커서 하지 않았다.
- **CI가 끝난 뒤에 빌드(workflow_run).** 단순하지만 31분 뒤에야 12분 빌드가 시작된다. 함께 돌리면 커밋에서 일반 채널까지 CI 시간 정도(약 31분)로 줄어든다.
- **헤르메스 설치기 셸처럼 앱은 그대로 두고 소스만 받기.** 헤르메스 런타임은 Python 소스라 git으로 바꿔 끼울 수 있다. SeuOffice는 Electron 묶음, Rust 엑셀 엔진, 한글 WASM을 빌드해야 하므로 사용자 PC에서 빌드를 돌려야 한다.

## 결과

- 커밋에서 일반 채널 설치본까지 약 31분에 1시간 확인 간격이 더해진다. 사람 단계는 안정 채널로 올리는 일 하나다.
- 미리보기 판이 푸시마다 생긴다. 일반 채널을 쓰는 사람(지금은 스풋)은 자주 업데이트 창을 본다.
- 판을 내는 실행(main 푸시와 `v*` 태그)은 모두 한 줄(concurrency `seuoffice-desktop-publish`)에 선다. 두 실행이 같은 판 번호를 함께 고르지 않는다. 릴리스 작업이 CI를 기다리는 동안 다음 실행은 기다리고, 그 사이 쌓인 푸시는 가장 새 것 하나만 판이 된다.
- 판 번호는 한 커밋만 가진다. 릴리스 작업은 올리기 전에 그 태그가 이미 다른 커밋을 가리키면 멈춘다(손으로 단 태그, 다른 커밋이 이미 낸 번호를 오래된 작업의 재실행이 다시 쓰는 경우). 확인과 만들기 사이에 태그가 끼어들면 만든 릴리스를 지우고 멈춘다. 확인은 저장소의 실제 태그(가벼운 태그)와 node 저장소의 주석 태그로 시험했다: 빈 번호 통과, 같은 커밋의 재실행 통과, 다른 커밋 거부, API 실패 시 멈춤.
- 손으로 `v*` 태그를 달아도 전처럼 그 판을 낸다. 그 판 번호가 다음 자동 판 번호의 기준이 된다.
