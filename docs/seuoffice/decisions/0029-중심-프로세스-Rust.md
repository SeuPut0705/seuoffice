# 0029 중심 프로세스를 Rust로: Node-API 애드온 하나, 모듈 통째로 묶음마다

- 날짜: 2026-11-12
- 상태: 확정(1묶음 진행 중)
- 결정한 사람: 메인 세션(스풋이 0025·0026의 2단계를 맡김)

## 맥락

결정 [0026](0026-화면은-React로-남긴다.md)의 2단계는 지금의 Electron main 프로세스를 Rust로 옮기는 일이다. 3단계에서 Electron이 빠지면 Rust 껍데기(Tauri 2나 CEF)가 이 코드를 그대로 쓴다. 2단계는 1단계(엔진)를 기다리지 않고, Electron이 남아 있는 동안 묶음마다 내보낸다.

`tools/main-inventory/inventory.ts`로 잰 크기(2026-11-12, main cfa4da21c 위):

- 모듈 377개, 131,840줄(시험 파일 빼고). 모듈은 앱의 `src/main` 바로 아래 파일이나 폴더 하나다. 앱 11개와 `packages/electron-utils`. 0025가 적은 "약 59,000줄"은 `apps/shell/src/main` 하나(56,090줄)다.
- `ipcMain` 등록 906곳. Electron API 이름 45개. 많이 쓰는 순서로 `ipcMain` 56모듈, `app` 43, `BrowserWindow` 35, `dialog` 35, `shell` 25, `webContents` 17.
- 네이티브 npm 애드온은 없다(`binding.gyp`, `prebuilds`, `node-gyp-build`를 찾음). pdf 쪽은 WASM(pdfium, qpdf)과 순수 JavaScript(pdf-lib, node-forge)다.
- Electron을 직접도, 가져오는 모듈을 거쳐서도 쓰지 않는 모듈은 257개, 44,722줄(34%)이다.

모듈별 표(줄, Electron API, IPC, 파일·OS, npm, 묶음)는 [중심-프로세스-목록.md](../중심-프로세스-목록.md)에 있고, 같은 도구가 다시 만든다.

물어야 할 것은 둘이었다. 지금의 Electron main이 Rust를 무엇으로 부르는가(애드온이냐 따로 도는 프로세스냐), 그리고 어떤 순서로 옮기는가.

## 결정

1. **Node-API 애드온 하나로 부른다.** 중심 프로세스의 Rust는 `crates/main-core`(Node도 Electron도 모르는 라이브러리)에 두고, `crates/main-node`(napi-rs 3)가 이것을 `.node` 애드온으로 감싸 Electron main이 `require`한다. 3단계의 Rust 껍데기는 `main-core`를 바로 링크한다. 같은 코드가 두 번 쓰이고, 다시 쓰는 것은 얇은 감싸개뿐이다.

   시제품 `crates/spike-main-bridge`로 잰 값(Mac mini, darwin-arm64, 마이크로초, 다섯 판의 중앙값):

   | 잰 것                          | Node 22 napi |    사이드카 | Electron 43 napi |    사이드카 |
   | ------------------------------ | -----------: | ----------: | ---------------: | ----------: |
   | JS → Rust, JSON 1 KB           |         10.9 |        21.2 |              9.6 |        23.4 |
   | JS → Rust, 1 MiB               |         88.3 |       1,146 |              159 |       1,521 |
   | Rust → JS → Rust               |          7.0 |        13.8 |              4.5 |         7.3 |
   | 시작(새 프로세스, 두 번째부터) |  1,414-2,454 | 2,910-4,252 |        792-1,212 | 2,515-2,871 |

   애드온이 작은 호출에서 두 배, 1 MiB에서 일곱에서 열 배 빠르고, 시작은 3분의 1이다. 둘 다 사람이 느낄 크기는 아니다. 고른 까닭은 부르는 쪽의 모양이다. 중심 프로세스는 설정·기록 파일을 동기로 읽는다(`readAppSettings`를 부르는 곳이 모두 동기). 동기 호출에 답할 수 있는 것은 애드온뿐이다. 사이드카로 가면 부르는 곳마다 비동기로 바꿔야 하고, 그것은 옮기는 일이 아니라 다시 짜는 일이다. 첫 실행의 약 20 ms와, 새로 복사한 바이너리를 처음 열 때의 300 ms는 시스템이 처음 보는 파일을 검사하는 값이다(시제품 README).

2. **애드온은 panic을 풀어서 JavaScript 오류로 바꾼다.** 작업 공간의 release 프로필은 `panic = "abort"`다(WASM 엔진). 애드온은 `node` 프로필(release를 물려받고 `panic = "unwind"`)로 짓는다. 그래야 Rust의 panic이 Electron main을 끝내지 않고, napi가 던지는 예외가 되어 지금의 TypeScript가 예외를 받던 자리에서 잡힌다.

3. **모듈을 통째로, 묶음으로 옮긴다.** 한 모듈은 한 묶음에만 든다. 묶음은 Rust로 옮기고, 비교를 통과하고, TypeScript 호출부를 애드온으로 돌리고, TypeScript 모듈을 지우는 데까지다. 묶음 규칙은 `inventory.ts`의 `batchOf`에 있고, 아래 줄 수는 그 도구의 출력이다.

   | 묶음 | 무엇                                                                                                              | 모듈 |     줄 | Electron 없음 | IPC |
   | ---- | ----------------------------------------------------------------------------------------------------------------- | ---: | -----: | ------------: | --: |
   | B1   | 셸의 기록과 설정: 업데이트 시도·캐시·채널·기록, 실행 경로, 앱 설정, 최근 파일, 창 크기, 충돌 기록, `atomic-write` |   15 |  2,274 |         2,274 |   0 |
   | B2   | `electron-utils`의 나머지(복구 저장소, 안전한 원격 주소, 내보내기 경로, 권한)                                     |   47 |  6,910 |         6,655 |   0 |
   | B3   | 셸의 저장소와 색인: 프로젝트, 파일 색인, 세션 기록, 실행 복구, 문서 연결, 폴더 트리                               |   40 | 13,967 |         4,300 |   0 |
   | B4   | 각 앱의 Electron 없는 모듈: 복구, 자산 수명, 위키 색인, 한글 탭 폭, 통합 문서 저장 판단                           |  141 | 19,660 |        17,151 |   0 |

   | B6   | Electron을 직접 쓰는 논리: 탭 관리, 분리 창, 렌더러 감시, 업데이터 배선, 글꼴 저장소                              |   29 |  7,821 |             0 |   0 |

   - B1부터 B4는 Electron 없이 옮겨진다. 순서는 B1 → B2 → B3 → B4. B2가 앞인 것은 모든 앱이 `electron-utils`를 쓰기 때문이다.
   - B5는 MCP SDK(`@modelcontextprotocol/sdk`)와 AI 공급자 호출을 Rust로 가져가야 한다. B1-B4 다음, 묶음 안에서 먼저 시제품으로 SDK를 정한다.
   - B6은 Electron 객체를 Rust로 넘기지 않는다. 모듈의 판단(창 위치 계산, 탭 상태, 감시 시간표)을 `main-core`로 옮기고, Electron을 부르는 몇 줄만 TypeScript에 남긴다. 그 몇 줄은 3단계에서 껍데기의 API로 바뀐다.
   - E는 2단계 묶음이 아니다. 그 라이브러리를 대신할 Rust가 1단계 엔진 흐름(pdf 등)에서 생길 때 함께 옮긴다.
   - S3는 3단계에서 옮긴다. 906곳의 IPC 등록은 Rust 껍데기의 명령 표가 된다. 2단계 동안 S3는 앞 묶음이 빠질수록 얇아진다.
   - 업데이터(`updater.ts`, electron-updater)와 `safeStorage`는 3단계까지 Electron에 남는다. 3단계는 지금 사용자를 보통의 자동 업데이트로 옮겨야 하고, 키체인에 든 비밀을 옮겨야 하기 때문이다. B1은 업데이터의 기록(시도, 캐시, 채널, 기록 파일)만 옮긴다.

4. **비교 틀은 `tools/main-diff`다.** `tools/docx-diff`와 같은 규칙: 같은 입력을 TypeScript와 Rust에 넣고 결과를 맞댄다. 중심 프로세스는 파일을 만지므로 입력에 폴더 상태(파일, 수정 시각, 권한)가 들고, 결과에 답(값, 오류의 `code`와 `message`, 기록 줄)과 호출 뒤 폴더가 든다. 양쪽은 각자 새 폴더에서 돌고, 경로는 `$DIR`로 바꿔 맞댄다. 차이는 `divergences.json`(까닭과 양쪽 답)에 적고, 적힌 차이가 더는 나지 않으면 틀이 실패한다. 함수마다 서로 다른 답이 둘 이상 나와야 한다. 러너의 `seuoffice rust` 작업이 돌린다.

5. **JavaScript와 Node의 뜻은 한 곳에.** `crates/README.md`의 규칙 그대로 JavaScript 연산은 `jscompat`에 하나씩 둔다. 중심 프로세스가 더 쓰는 것: Node의 `path`(posix와 win32 둘, Node 22 `lib/path.js`를 옮김, `jscompat::node_path`), `Date.parse`(docx 엔진에 있던 V8 이식을 `jscompat`으로 옮김), `JSON.stringify(v, null, 2)`. Node의 파일 오류(`code`와 `message`)는 libuv의 이름과 문구로 `main-core::node_fs`가 만든다.

6. **애드온은 판마다 플랫폼별로 짓는다.** Mac은 arm64와 x64를 `lipo`로 합친 하나, Windows x64, Linux x64. `.node`는 asar 밖에 두고(`asarUnpack`) 앱과 함께 서명한다. Node-API는 ABI가 고정이라 Electron 판을 올려도 다시 지을 필요가 없다. 이 배선은 B1의 마지막(호출부를 애드온으로 돌리는 커밋)에서 한다.

## 버린 대안

- **사이드카 프로세스(Rust 실행 파일, 표준 입출력의 길이 붙은 틀).** 충돌이 나도 Electron main이 살아남는 것이 장점이다. 버린 까닭: 동기 호출에 답하지 못해 부르는 곳을 모두 비동기로 다시 짜야 한다. 위 표대로 느리고(1 MiB에서 열 배), 프로세스 하나를 더 띄우고 지키고 서명해야 한다. panic은 결정 2로 예외가 된다.
- **WASM을 Electron main에서 돌리기.** 1단계 엔진처럼 `wasm32-wasip1`로 지어 `node:wasi`로 부르는 길. 버린 까닭: 중심 프로세스의 일은 파일, 프로세스, OS 호출이고 WASI는 그 일부만 준다. Node의 WASI는 아직 실험 단계다. 3단계의 Rust 껍데기는 WASM 실행기를 따로 품어야 한다.
- **3단계에서 한꺼번에.** Electron을 걷어 낼 때 중심 프로세스도 같이 옮기는 길. 버린 까닭: 13만 줄을 한 번에 바꾸면 내보낼 수 있는 중간이 없고, 비교 틀로 하나씩 확인할 수 없다.
- **S3(IPC와 창)도 2단계에서.** 버린 까닭: `BrowserWindow`, `webContents`, `dialog`는 Electron 객체라 Rust가 쥘 수 없다. 넘기려면 Electron API 전체를 애드온 너머로 다시 감싸야 하고, 그 감싸개는 3단계에서 버려진다.
- **기존 Rust 크레이트(예: `path-clean`, `normpath`)로 경로 처리.** Node의 `path`와 다르게 답한다(`..`가 앞에 남는 경우, Windows 드라이브 상대 경로, `\\?\` 장치 경로). 저장된 설정의 키가 경로이므로 한 글자 차이도 설정을 잃는다.

## 결과

- 새 크레이트 `main-core`, `main-node`가 `crates/` 작업 공간에 든다. 러너의 `seuoffice rust`가 clippy와 시험, `main-diff` 비교를 돌린다.
- B1은 옮김과 비교까지 이 가지(`feat/rust-stage2-plan`)에 있고, 호출부 전환과 애드온 꾸리기는 B1의 마지막 커밋으로 남았다. 전환 전까지 제품은 TypeScript를 그대로 쓴다.
- B1의 첫 비교(러너 실행 43241830975, 고치기 전, `tools/main-diff/first/b1-gate.txt`): 함수 138개에 18,839번 맞대어 18,831번 같았다. 다른 8번은 네 갈래다. 비교 틀의 디스패처가 `undefined`를 잘못 넘긴 2번은 고쳤고, `path.posix.relative`가 서로게이트 쌍을 자른 1번(Rust 문자열은 짝 없는 서로게이트를 담지 못함)과 `path.format`에 문자열이 아닌 값을 준 5번(타입 밖의 입력)은 `divergences.json`에 적었다. 고친 뒤 러너(실행 43244730053)에서 다른 것 0, 적힌 것 6. 함수마다 서로 다른 답이 둘 이상이다(상수 넷은 하나뿐이라 면제). 결함을 심어 잡히는지 보는 일은 아직 하지 않았다.
- Windows의 경로와 파일 오류는 러너가 Linux라 비교하지 못한다. `path.win32`는 어느 플랫폼에서나 돌므로 비교되고, Windows 오류 번호를 Node 이름으로 바꾸는 표(`node_fs.rs`)는 Windows 러너에서 확인해야 한다.
- 시제품은 Mac arm64에서만 쟀다. Windows와 x64, 메모리는 재지 않았다.
