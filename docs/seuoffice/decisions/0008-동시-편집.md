# 0008 동시 편집

- 날짜: 2026-11-09
- 상태: 확정. 1번(실시간 공동 편집은 하지 않는다)은 결정 0023이 뒤집었다. 잠금 흐름은 어댑터가 없는 형식에 남는다
- 결정한 사람: 메인 세션(스풋이 2026-11-08에 남은 단계를 모두 진행하라고 맡김). 스풋이 뒤집을 수 있다.

## 맥락

5단계는 동시 편집을 설계한다. 2단계는 단일 편집자 잠금이다. 붙이는 쪽(유유 앱)이 잠금을 잡은 경우에만 `mode: 'edit'`로 열고, 저장은 `onSave`로 붙이는 쪽에 돌아간다(`README.md` "웹에서 열기").

다섯 앱은 문서 모델이 모두 다르다.

| 앱   | 편집 중 문서 모델                             | 사는 곳                                                        |
| ---- | --------------------------------------------- | -------------------------------------------------------------- |
| docx | `@genoffice/docx-engine` 모델과 렌더러 편집기 | 렌더러                                                         |
| xlsx | Univer 화면 모델 + Rust 엔진 세션             | 렌더러 + wasm 워커                                             |
| pptx | `pptx-engine` 세션 상태                       | 데스크톱은 main, 웹은 페이지(`apps/slides/src/web/session.ts`) |
| hwp  | rhwp(Rust wasm) 문서                          | 스튜디오 iframe                                                |
| pdf  | pdf.js 화면 + 저장 때 pdf-lib 쓰기            | 렌더러                                                         |

실시간 동시 편집(여러 사람이 같은 문서를 같은 순간에 고치는 것)은 앱마다 편집 연산을 공유 모델(CRDT나 OT)로 옮겨야 한다. 다섯 모델 모두 그런 연산 층이 없다. 이 저장소에 Yjs나 Automerge 같은 공유 모델 라이브러리도 없다(`node_modules` 확인). 상위(이음오피스, GenOffice)에도 계획이 없다. 이 일을 하면 상위를 따라가는 비용이 커진다. 앱 편집 코드의 거의 모든 곳을 고치게 되기 때문이다.

## 결정

1. 동시 편집의 기본은 잠금이다. "한 문서는 한 사람이 고치고, 다른 사람은 그동안 읽는다"를 제품 동작으로 둔다. 실시간 공동 편집은 하지 않는다.
2. 잠금은 붙이는 쪽이 가진다. seuoffice는 잠금 서버를 두지 않는다. 붙이는 쪽이 할 일은 아래와 같다.
   - 열기 전에 잠금을 잡는다. 성공하면 `mode: 'edit'`, 실패하면 읽기 모드로 연다. 실패하면 누가 고치고 있는지 보여 준다.
   - 잠금에 만료 시간을 두고, 편집 화면이 열려 있는 동안 연장한다. 창이 닫히거나 연결이 끊긴 채 만료되면 잠금을 푼다.
   - `onSave`에서 잠금이 아직 자기 것인지 확인한다. 아니면 거절한다(`throw`). 거절하면 seuoffice 화면이 저장 실패로 보이고 문서는 고친 상태로 남는다.
   - 저장마다 새 판을 만들고, 열 때 받은 판 위에 저장하는지 확인한다(낙관적 충돌 검사). 판이 다르면 거절한다.
   - 읽는 사람이 최신 판을 보도록, 새 판이 생기면 읽기 화면을 다시 연다(`destroy` 뒤 `openDocument`).
3. 넘겨주기: 편집 중인 사람에게 넘겨 달라고 요청하면, 붙이는 쪽이 그 화면에서 `doc.save()`를 부르고 잠금을 푼다. 그다음 요청한 사람이 잠금을 잡는다. seuoffice 쪽은 이미 있는 `save()`로 충분하다.
4. 실시간 공동 편집은 다시 검토할 조건을 정해 둔다. 아래가 생기면 이 결정을 다시 연다.
   - 한 형식(가장 가능성이 높은 것은 xlsx)에서 같은 문서를 동시에 고쳐야 하는 업무가 실제로 생겼다.
   - 그 형식의 편집 모델에 연산 단위 공유를 붙일 수 있는 상위 또는 라이브러리 경로가 확인됐다.

## 버린 대안

- 형식마다 CRDT로 실시간 공동 편집: 다섯 모델을 모두 다시 짜야 한다. 상위를 따라가기도 어려워진다. 지금 업무 요구(유유 메신저 첨부 고치기)에 비해 너무 크다.
- seuoffice가 잠금 서버를 둠: seuoffice는 서버 없이 정적 파일과 부품만 내놓는다(0005). 사용자와 권한은 붙이는 쪽이 이미 안다.
- 저장된 판끼리 형식별 3방향 병합: docx, xlsx, hwp 모두 병합 규칙이 형식마다 다르고, 실패하면 사람이 풀어야 한다. 잠금이 있으면 병합할 일이 생기지 않는다.
- 문단·시트 단위 잠금: 앱마다 편집 범위를 나눠 막아야 해서 실시간 편집과 거의 같은 양의 앱 수정이 든다.

## 결과

- seuoffice 쪽에 더할 코드는 없다. 2단계 계약(`mode: 'edit'`, `onSave` 거절, `onDirtyChange`, `save()`)이 잠금 흐름을 모두 받친다.
- 유유 쪽(yuyu-mos)이 잠금, 만료·연장, 판 검사, 넘겨주기를 만든다. README에 붙이는 쪽 규칙을 적는다.
- 5단계는 이 결정으로 끝낸다. 실시간 공동 편집은 위 조건이 생길 때 새 단계로 연다.
