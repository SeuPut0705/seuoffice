# 0010 PDF 웹 저장은 데스크톱 저장 코드를 그대로 쓴다

- 날짜: 2026-11-09
- 상태: 확정

## 맥락

PDF 앱은 저장할 때 렌더러가 보류 중인 편집을 `SavePdfRequest` 하나로 모아 메인 프로세스에 넘기고, 메인 프로세스의 `applySaveRequest`(`apps/pdf/src/main/save-pdf.ts`)가 원본 바이트에 적용한다. 단계 대부분(주석 마크업, 도형·메모·잉크·링크·이미지 스탬프, 메모 고치기, 양식 값·필드, 빈 페이지, 회전, 삭제, 순서, 메타데이터, 책갈피, 첨부)은 `pdf-lib`만 쓴다. 나머지 단계는 데스크톱 엔진이 있어야 한다.

- 텍스트 편집·추가, 이미지 편집, 저장된 주석 삭제, 영구 제거: pdfium(파일 시스템에서 wasm을 읽음), 시스템 글꼴, Electron `nativeImage`
- 암호 보호: Node `crypto`의 AES

`save-pdf.ts`는 이 모듈들을 정적으로 들여오므로 웹 묶음에 그대로 넣으면 `node:module`에서 빌드가 깨진다.

## 결정

- 웹 저장은 `applySaveRequest`를 그대로 부른다. 앱 웹 설정(`apps/pdf/vite.web.config.ts`)의 플러그인이 데스크톱 엔진 단계 모듈(`pdf-crypt`, `atomic-write`, `redaction`, `text-edit`, `image-edit`, `annot-delete`, `annot-flatten`)을 `apps/pdf/src/web/desktop-stages.ts`로 바꿔 끼운다. 그 대역은 불리면 `WebUnsupportedError`를 던진다.
- `apps/pdf/src/web/save.ts`는 요청에 데스크톱 전용 편집이 하나라도 있으면 아무것도 적용하지 않고 `{ ok: false, error }`로 거절한다. 렌더러는 기존 "저장 실패" 상태로 그 까닭을 보여 주고 편집을 보류 상태로 남긴다. 일부만 저장하지 않는 까닭은, 성공한 저장 뒤 렌더러가 요청에 담긴 편집을 모두 지우므로 걸러 낸 편집이 소리 없이 사라지기 때문이다.
- 저장된 바이트는 호스트가 받아들인 뒤에만 페이지의 문서 바이트가 되고, 렌더러는 저장 뒤 다시 읽을 때 그 바이트를 연다.
- 호스트가 저장을 요청하면 데스크톱 셸이 쓰는 닫기 저장 요청(`onCloseSaveRequest`, `flushAll: true`)으로 렌더러 자신의 저장을 돌린다.

## 버린 대안

- `pdf-lib` 단계를 웹 쪽 새 파일로 옮겨 쓰기: 약 1,000줄을 베끼게 되고 이음오피스를 따라갈 때마다 두 벌을 맞춰야 한다.
- `@seuoffice/web-platform`에 `node:module` 흉내를 더해 모든 단계를 묶기: pdfium 연결 코드와 글꼴 처리 코드까지 묶음에 들어가지만, 결국 파일 시스템 흉내에서 실패한다. 다른 앱이 함께 쓰는 패키지도 건드리게 된다.
- 상위 `save-pdf.ts`를 쪼개기: 상위 편집이 크다.

## 결과

- 웹 편집 모드에서 `pdf-lib` 단계 편집은 데스크톱과 같은 코드로 저장된다.
- 텍스트·이미지 편집, 저장된 주석 삭제, 영구 제거, 암호 보호는 웹에서 저장을 거절한다. 브라우저에서 pdfium을 불러오는 방법(wasm을 `fetch`로 읽기)이 생기면 그 단계부터 대역에서 빼낸다.
- `save-pdf.ts`가 새 데스크톱 모듈을 정적으로 들여오면 웹 빌드가 깨져서 바로 드러난다. 그때 대역 목록에 더한다.
