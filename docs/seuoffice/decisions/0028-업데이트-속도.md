# 0028 앱 안 업데이트를 빠르게: 바뀐 블록만 받고, 기다림을 덜어 낸다

- 날짜: 2026-11-12
- 상태: 확정
- 결정한 사람: 메인 세션(스풋이 "업데이트 설치가 너무 오래 걸린다, 빠르게"를 맡김)

## 맥락

스풋 PC(Windows, 부하 큰 상태)에서 0.12.35 업데이트는 내려받기 22-23초(215 MB), "다시 시작 및 설치"에서 앱 창까지 141-179초였다. 단계별로 보면 설치 프로그램 시작 뒤 옛 언인스톨러가 파일을 지우기 시작하기까지 34초를 거의 CPU 없이 기다렸고(9.9 + 24.2초), 파일 5767개 지우기 10.4초, 압축 풀기와 쓰기 88초, 설치 뒤 앱 시작까지 11.8초였다. Mac은 zip을 `ditto`로 풀고 번들 전체를 `codesign --verify --deep --strict`로 확인한 뒤 바꿔 끼운다.

업데이트는 늘 설치 파일 전체를 받았다(`disableDifferentialDownload = true`, "full-package policy": 릴리스에 설치 파일과 `latest.yml`만 있으면 되게 하려던 것). 그런데 릴리스는 이미 `.blockmap`을 함께 올리고 있다(결정 0013의 열네 파일).

## 결정

1. **바뀐 블록만 받는다(차등 다운로드).** `updater.ts`가 `disableDifferentialDownload = false`로 둔다. electron-updater가 앞 판과 새 판의 `.blockmap`을 비교해 바뀐 블록만 받고, 나머지는 지금 판의 사본에서 가져와 새 파일을 만든 뒤 피드의 sha512로 확인한다. 사본은 Windows 설치 프로그램이 설치할 때마다 남기는 `installer.exe`, Mac은 electron-updater가 내려받을 때마다 남기는 `update.zip`이다. 그래서 `update-cache.ts`는 `installer.exe`를 더는 지우지 않는다. 앞 판의 blockmap이 없거나(지운 프리릴리스), 사본이 없거나(차등을 켠 뒤 첫 업데이트), 만든 파일이 sha512에 맞지 않으면 electron-updater가 파일 전체를 받는다(`tests/update-differential.test.ts`가 electron-updater의 코드로 네 경우를 확인).
   - 0.12.34 → 0.12.35: Windows 215.1 MB 중 18.7 MB(8.7%), Mac 260.6 MB 중 47.0 MB(18.0%). 0.12.30 → 0.12.35(144커밋): Windows 25.5 MB, Mac 52.7 MB. 릴리스의 실제 blockmap으로 electron-updater의 계획 함수(`computeOperations`)를 돌려 셈했다.
2. **Windows 설치 파일은 앱을 zip으로 싣는다(`nsis.useZip`).** 기본 7z 꾸러미는 임시 폴더에 푼 다음 설치 폴더로 다시 복사하고, 끝나면 임시 폴더를 지운다(스풋 PC에서 설치 프로그램이 앱 창이 뜬 뒤에도 8초 더 돈 까닭). zip은 설치 폴더에 바로 푼다. GitHub Windows 러너(실행 43202286009)에서 0.12.35 위로 조용한 업데이트 설치가 58.5-59.3초에서 28.2-29.2초로, 새로 설치가 48.5-52.5초에서 19.9-21.6초로 줄었다. 설치 파일은 205 MB에서 269 MB로 커진다. electron-builder는 설치 파일의 `.blockmap`을 7z 꾸러미일 때만 만들므로 `electron-builder.seuoffice.cjs`가 `artifactBuildCompleted`에서 직접 만든다(electron-builder의 `buildBlockMap`, 같은 내용 기준 블록 나누기). 릴리스 작업은 이미 이 파일이 있는지 확인하고 올린다.
3. **업데이트의 언인스톨에서 PATH와 탐색기 알림을 건너뛴다.** 옛 판의 언인스톨러가 `--updated`로 돌 때 명령줄의 PATH 항목을 지우고 모든 창에 알렸다가(창마다 최대 5초 기다리는 `WM_WININICHANGE` 방송), 새 설치 프로그램이 다시 넣고 또 알렸다. 설치 폴더가 그대로이니 둘 다 할 일이 없다. 연결 프로그램의 탐색기 새로 고침도 설치 프로그램이 곧 한 번 한다. 언인스톨러는 설치된 옛 판의 것이 돌므로, 이 효과는 이 판이 깔린 다음 업데이트부터 난다.
4. **Mac은 새 앱을 먼저 열고 옛 번들을 지운다.** 바꿔 끼우기 스크립트가 700 MB 옛 번들을 지운 다음 앱을 열던 순서를 바꿨다(러너에서 0.6-0.8초).
5. **업데이트 기록에 단계마다 시각을 남긴다.** `update-log.txt`에 `phase <단계>` 줄(확인, 내려받기와 받은 바이트, Mac 풀기와 서명 확인, 다시 시작 요청, will-quit, 설치 프로그램·바꿔 끼우기 시작, 스크립트의 swap-start·relaunch)을 쓰고, 새 판의 첫 시작이 설치 프로그램 시작부터 걸린 초를 `app-started since-install-start-s=`로 남긴다.

함께 고친 결함: 설치 프로그램이 앱을 다시 연 뒤 몇 초 더 돌며 자기 파일을 잡고 있어 첫 시작의 캐시 정리가 매번 EPERM으로 실패했다(이제 30초마다 네 번 다시 한다). 내려받는 중에도 정해진 확인이 돌았고, 그 확인이 실패하면 같은 `error` 사건이 내려받기를 실패로 표시했다(이제 내려받는 동안과 받은 뒤에는 확인하지 않고, 내려받기 실패는 `downloadUpdate()`의 거절로만 센다).

## 버린 대안

- **Mac 서명 확인을 얕게(`codesign --verify`).** 러너에서 깊은 확인 2.9-4.3초, 얕은 확인 0.5-0.6초. 깊은 확인은 번들 안 모든 파일이 서명과 맞는지 보는 마지막 안전장치이고, 업데이트 전체에서 차지하는 몫이 작아 두었다(`ditto` 풀기 4.0-4.7초).
- **압축 끄기(`compression: store`)나 통째 압축(solid 7z).** 같은 러너에서 업데이트 설치가 각각 64.9-69.5초, 61.4-62.1초로 기본(58.5-59.3초)보다 느렸다. 7z 플러그인의 풀기와 복사가 병목이라 압축률은 상관이 없다. store는 설치 파일이 769 MB가 된다.
- **설치 프로그램의 "앱이 도는가" 확인(PowerShell 세 번)을 바꾸기.** 러너에서 1.8-2.2초라 손대지 않았다.

## 결과

- 릴리스는 지금처럼 `.blockmap`을 올려야 한다. 빠지면 업데이트가 조용히 전체 받기로 돌아간다.
- 차등 다운로드는 범위 요청을 여러 번 보낸다(GitHub 공급자는 한 요청에 한 범위, 0.12.34 → 0.12.35에 Windows 34번, Mac 370번). 느린 연결에서도 받는 바이트가 줄어 빠르지만, 실제 시간은 스풋 PC에서 확인한다.
- zip으로 바꾼 첫 판은 앞 판(7z)과 블록이 거의 맞지 않아, 그 판으로 가는 Windows 업데이트는 전체에 가깝게 받는다. 그다음 판부터 바뀐 블록만 받는다.
- zip 풀기는 7z 경로처럼 잠긴 파일을 몇 번 다시 시도하지 않는다. 설치 프로그램은 풀기 전에 앱 프로세스를 끝내고 옛 파일을 옮겨 두므로 잠긴 파일이 남을 일은 드물지만, 풀기가 실패하면 7z 경로와 마찬가지로 옛 판도 없는 설치가 남는다(옛 파일은 언인스톨 단계에서 이미 지워진다).
