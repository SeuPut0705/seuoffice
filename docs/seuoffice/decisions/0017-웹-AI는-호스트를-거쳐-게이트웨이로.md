# 0017 웹 AI는 호스트를 거쳐 게이트웨이로

- 날짜: 2026-11-09
- 상태: 확정
- 결정한 사람: U13 작업 세션(메인 세션이 맡김). 스풋이 뒤집을 수 있다.

## 맥락

결정 0009 "웹"은 방향만 정했다. iframe 페이지는 토큰을 갖지 않고 게이트웨이를 부르지 않는다. 페이지가 embed 통로로 호스트에 묻고, 호스트가 자기 로그인으로 게이트웨이를 불러 돌려준다. 요청과 응답은 `gateway-complete` 모양(OpenAI Chat Completions 요청, SSE 스트림)을 그대로 둔다. 메시지 이름, 취소와 오류 전달은 이 단위가 정한다.

이 단위 전의 사실:

- embed 통로는 `open`·`save`·`dirty`·`request_save`만 날랐다. `@seuoffice/embed`에 AI 자리가 없었다.
- 다섯 앱(docs, hwp, slides, sheets, pdf)의 렌더러가 같은 세 메서드로 AI를 부른다: `aiStream(request)`, `aiStreamCancel(requestId)`, `onAiStream(handler)`. 웹 브리지에서는 셋이 없거나 `WebUnsupportedError`였고, `getAiSettings`는 기본값(아무것도 연결 안 됨)이었다.
- 데스크톱은 메인 프로세스 `ai:stream`이 `streamForProvider`(`packages/ai-provider/src/stream.ts`)를 부르고, 그 안의 `aiFetch`(`fetch.ts`)가 전역 `fetch`로 게이트웨이에 요청한다.

## 결정

### 통로 메시지

모든 메시지는 기존 봉투(`source: 'seuoffice'`, `version: 1`)에 담긴다. `version`은 올리지 않는다. 새 필드와 메시지를 모르는 쪽은 그것을 무시하고, 그러면 AI가 "연결 안 됨"으로 보일 뿐이다.

| 방향            | 메시지       | 필드                                                   | 뜻                                                                                                             |
| --------------- | ------------ | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 호스트 → 페이지 | `open`       | `ai: boolean`(더함)                                    | 호스트가 AI를 내주는지. 참이면 페이지가 `gateway` 제공자를 고르고 설정된 것으로 보인다                         |
| 페이지 → 호스트 | `ai_request` | `requestId: string`, `body`                            | 데스크톱이 보낼 `gateway-complete` HTTP 요청 본문 그대로(JSON 객체). 페이지의 프로토콜 코드가 만든다           |
| 호스트 → 페이지 | `ai_chunk`   | `requestId`, `data: Uint8Array`, 첫 메시지만 `headers` | 게이트웨이 응답 바이트(SSE) 그대로. 받은 차례대로 보낸다                                                       |
| 호스트 → 페이지 | `ai_end`     | `requestId`, 본문이 비었으면 `headers`                 | 응답 본문이 끝났다                                                                                             |
| 호스트 → 페이지 | `ai_error`   | `requestId`, `status?: number`, `headers?`, `message`  | 2xx가 아닌 응답이면 `status`, `headers`와 응답 본문(64 KiB까지). 호스트가 부르지 못했으면 `status` 없이 이유만 |
| 페이지 → 호스트 | `ai_cancel`  | `requestId`                                            | 페이지가 그 요청을 그만 읽는다. 호스트는 게이트웨이 요청을 끊는다                                              |

- 요청 여러 개가 동시에 오갈 수 있다. `requestId`는 페이지가 만든다(`crypto.randomUUID()`).
- 호스트는 `open`을 보낸 뒤에, 그 iframe 창과 seuoffice 출처에서 온 `ai_request`·`ai_cancel`만 받는다(저장과 같은 규칙). 페이지는 `open`을 보낸 창과 출처에서 온 `ai_chunk`·`ai_end`·`ai_error`만 받는다.
- 이미 진행 중인 `requestId`로 다시 온 `ai_request`는 버린다. AI를 내주지 않는 호스트는 `ai_request`에 `ai_error`로 답한다.
- `headers`는 게이트웨이 응답 머리글 중 `content-type`과 `retry-after` 둘뿐이다(있을 때만). 쿠키 등 나머지는 넘기지 않는다. 한 응답의 첫 메시지(`ai_chunk`, 본문이 비면 `ai_end`, 또는 상태 있는 `ai_error`)에만 실린다. 페이지는 이 둘을 `Response` 머리글로 넣어, 데스크톱 프로토콜이 `application/json` 2xx 답을 따로 읽고 `Retry-After`가 20초를 넘는 혼잡 응답은 다시 보내지 않는 판단을 그대로 한다.

### 취소와 오류

- 페이지 쪽 취소(사용자가 멈춤을 누름, 응답 본문을 버림, 페이지가 내려감(`pagehide`)): 페이지가 `ai_cancel`을 보내고 그 요청의 응답을 더 받지 않는다. 그 뒤에 온 메시지는 버린다. 렌더러에는 데스크톱처럼 `done`이 간다. 페이지가 내려가면 진행 중인 요청 모두에 `ai_cancel`을 보낸다.
- 호스트가 `ai_end`나 `ai_error`를 보낸 뒤라도 페이지가 아직 다 읽지 않은 바이트는 취소하면 버려지고 본문 읽기는 `AbortError`로 끝난다(fetch와 같다). 이때 호스트는 이미 끝났으므로 `ai_cancel`은 보내지 않는다.
- `ai.request`가 `signal`을 무시하고 취소 뒤에 응답을 돌려줘도, 호스트는 그 응답 본문을 버리고 페이지에 보내지 않는다.
- 호스트는 `ai_cancel`을 받으면 `ai.request`에 넘긴 `AbortSignal`을 끊고, 읽던 응답 본문도 멈춘다. 끊긴 요청에는 아무것도 더 보내지 않는다.
- `destroy()`는 진행 중인 요청을 모두 끊는다.
- 2xx가 아닌 응답(`ai_error`에 `status`): 페이지는 그 상태 번호와 본문을 가진 HTTP 응답으로 프로토콜 코드에 넘긴다. 그래서 401·403(토큰 거절), 429·503·529(혼잡, 다시 보내기), 출력 한도 거절이 데스크톱과 같은 코드로 처리된다. 다시 보내기는 새 `ai_request`다.
- `status` 없는 `ai_error`: 페이지에서는 네트워크 실패처럼 보인다. 응답 도중이면 페이지는 이미 받은 바이트를 먼저 읽고 그 이유로 끊긴다(그때까지 나온 글은 남는다).
- 페이지는 응답을 기다리는 시간을 따로 재지 않는다. 데스크톱 프로토콜의 감시 시간(첫 응답, 조각 사이 침묵)이 그대로 돈다.

### 페이지 쪽

- `@seuoffice/web-platform`의 `requestAiFromHost(body, signal)`이 통로 위의 `fetch`다. `ai_chunk`가 본문 `ReadableStream`을 채우는 `Response`를 돌려준다.
- `ai-relay.ts`가 그 위에 `fetch` 모양 전송(`hostAiFetch`)을 둔다. 받는 주소는 `https://embed-host.invalid/chat/completions` 하나뿐이고, 다른 주소는 `TypeError`로 거절한다. `.invalid`는 풀리지 않는 이름이라 무엇이 새어도 네트워크로 나가지 않는다.
- `createAiStreamBridge()`가 브리지 세 메서드를 만든다. 요청마다 `streamForProvider('gateway', …)`를 부른다. 요청 본문 조립, SSE 해석, 도구 호출 조각 잇기, 오류 분류는 데스크톱 코드 그대로다. 페이지에 두 번째 파서는 없다.
- `webAiSettings()`: 호스트가 AI를 내주면 `provider: 'gateway'`, `providers.gateway.baseUrl`이 위 주소인 설정. 아니면 기본값이다. 렌더러의 "연결 안 됨" 판단(`isKeyProviderConfigured`, 보내기 문)은 손대지 않았다.
- 프로토콜은 토큰이 비면 보내지 않는다. 페이지는 자리만 채우는 고정 글자(`held-by-the-embed-host`)를 토큰 공급자로 등록한다. 그 글자는 그 요청의 `Authorization` 머리글에만 들어가고, 통로는 머리글을 버리고 본문만 보낸다. 진짜 토큰은 페이지에 오지 않는다.
- 모델 칸은 힌트다. 웹 설정에서는 비어 있어(`model: ''`) 게이트웨이가 고른다.
- docs, hwp, sheets, pdf의 웹 브리지가 같은 도우미를 쓴다. PDF도 같은 세 메서드를 쓰므로 들어갔다. slides는 세 메서드를 연결했지만 `getAiSettings`가 기본값이라 "연결 안 됨"으로 보인다. slides AI 패널은 실행 전에 `beginHistoryBatch`·`aiRunBegin`(결정 0012의 덱 기록과 잠금)을 부르는데 웹 브리지가 둘 다 거절해, 켜 두면 모든 요청이 실패하기 때문이다. 다음 단위에서 웹 덱 기록을 만든 뒤 켠다.

### 상위 파일 고침

- `packages/ai-provider/src/fetch.ts`에 `setAiFetch(fn)`을 더했다. `aiFetch`가 전역 `fetch` 대신 쓸 함수다. 데스크톱은 부르지 않으므로 동작이 같다.
- 페이지 묶음이 `stream.ts`를 끌어오면 구독 CLI 코드가 `node:string_decoder`·`node:http`를 가져온다. 웹에서는 돌지 않는 길이라, 웹 층 shim 생성기에 두 모듈을 더했다(부르면 `WebUnsupportedError`).

### 호스트가 할 일

`openDocument`의 `ai.request(body, signal)`은 사람의 토큰으로 유료 API를 부르는 자리다. 호스트가 책임진다.

- 로그인한 사람의 토큰을 호스트 쪽에서 붙인다. 토큰을 iframe에 넘기지 않는다. 받은 `body`를 그대로 게이트웨이에 넘기는 것이 기본이고, 필요하면 `model`을 바꾸거나 크기를 검사해 거절해도 된다.
- 누가 AI를 쓸 수 있는지 정한다. 쓸 수 없는 사람에게는 `ai`를 넘기지 않는다(페이지는 "연결 안 됨"을 보이고 아무것도 보내지 않는다).
- 사람마다, 문서마다 요청 수와 토큰 양을 제한한다. 한 턴은 도구를 부를 때마다 요청을 하나 더 보내고, 혼잡 응답(429·503)에는 두 번까지 다시 보낸다. 거절할 때는 2xx가 아닌 응답(예: 429)을 돌려주면 페이지가 데스크톱과 같은 문구로 보인다.
- `signal`을 게이트웨이 `fetch`에 넘겨 취소가 요금을 멈추게 한다.
- 오류 본문에 토큰을 싣지 않는다. 그 본문은 페이지에 그대로 간다.
- seuoffice 웹 묶음은 호스트가 믿는 출처에서만 서빙한다. 그 출처의 페이지가 보낸 `ai_request`는 호스트가 사용자 대신 부르는 요청이 된다.

## 결과

- 호스트가 `ai`를 주면 docs, hwp, sheets, pdf의 AI 패널이 웹에서 돈다. docs AI 편집은 데스크톱처럼 변경 추적(`AI Assistant`)으로 남는다(결정 0009). sheets의 AI 편집은 제안으로 들린다(결정 0012, 웹 시험으로 확인). hwp는 연결했지만 웹에서 AI 한 턴을 돌려 보지 않았다.
- slides는 호스트가 `ai`를 주어도 "연결 안 됨"이다(위 "페이지 쪽"). 웹 시험이 이것을 확인한다.
- 호스트가 `ai`를 주지 않으면 지금처럼 "연결 안 됨"이고 아무것도 보내지 않는다.
- 그대로 남은 웹 차이: 첨부, 그림 만들기, 웹 검색·주소 읽기, 구독, `aiChat`, `aiToolCapabilities`, slides의 AI 제안 메서드(`aiRunBegin`, `aiRunHold`, `aiProposalAccept`, `aiProposalReject`).
- `@seuoffice/embed`의 공개 API에 `ai?: AiRelay`와 `AiRelay` 형이 더해졌다. 판 번호는 올리지 않았다.
