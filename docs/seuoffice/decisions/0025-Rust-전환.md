- 상태: 확정(1단계 진행 중). 2항과 4단계(화면을 Rust로)는 [0026](0026-화면은-React로-남긴다.md)이 대신한다
- 결정한 사람: 스풋("seuoffice를 Rust로 변환하라", 화면까지 Rust로 다시 만든다). 엔진의 모양은 메인 세션이 설계안 두 개를 견주어 정했다
- 앞서 스풋이 이 세션에서 "Tauri/Rust 전환은 진행하지 말고"라고 했던 것을 스풋이 거두었다(질문 창에서 직접 확인)

## 맥락

앱은 Electron과 TypeScript로 되어 있다. 엑셀 엔진(`apps/sheets/native/xlsx-engine`, Rust 32,460줄)과 한글 엔진(rhwp, Rust → WASM)만 Rust다. 스풋이 앱 전체를 Rust로 옮겨 가볍고 빠른 고유 앱으로 만들라고 했다. 재 보고 정하자는 제안은 스풋이 물렸다. 측정은 조건이 아니고, 옮기면서 전후 수치를 남긴다.

## 결정

1. **순서.** 엔진(워드부터, 이어서 pptx, odt, epub, file-parse) → 중심 프로세스 → Electron 제거 → 화면. 단계마다 `main`에는 돌아가는 앱이 남는다.
2. **화면까지 Rust로 간다.** 화면 도구(GPUI 등)는 4단계에서 고른다. 그때까지 화면은 지금의 React다.
3. **브라우저판은 React와 WASM 엔진으로 남는다.** `apps/web`과 임베드는 Rust 화면 도구로 갈 수 없다. 그래서 엔진은 모두 네이티브와 `wasm32-wasip1` 둘 다로 빌드한다. 엑셀 엔진이 이미 그렇게 한다.
4. **워드 엔진의 모양: 지금 모델을 그대로 잇고 제자리에서 바꾼다.** Rust 엔진이 지금의 `ParsedDoc` 모델을 그대로 내고, TypeScript 엔진의 모듈을 하나씩 지워 간다. 내보낸 함수 하나에 구현은 늘 하나다. 호출하는 464곳은 얇은 바인딩 뒤에서 그대로 돈다.
5. **검사 틀이 먼저다.** 묶음마다 TypeScript 엔진(그 묶음을 시작한 커밋)과 Rust 엔진의 결과를 저장소의 문서 전체에서 맞대 본다. 읽기는 모델이 같아야 하고, 저장은 zip 항목의 이름·순서·내용이 같아야 한다. 차이는 까닭과 함께 적은 것만 허용한다. 비교한 수가 정해 둔 바닥보다 적으면 통과가 아니다.
   - **묶음으로 옮긴다**(스풋, 2026-11-12: "조금씩 작업하고 검사하면 하루종일하잖아"). 한 묶음은 엔진 하나(워드는 읽기와 쓰기 둘)를 통째로 옮긴 것이다. 비교 검사는 묶음 끝에 한 번 돌리고, 결함 주입과 장부 정리는 `main`에 합치기 전에 한 번 한다. 무거운 검사는 러너에서 돌리고 세션은 결과를 기다리지 않고 다음 묶음을 시작한다. 대가: 차이가 나오면 큰 묶음 안에서 원인을 찾는다.
   - 그대로 두는 마지막 관문: `main`에 합치기 전에 비교 검사 전부, 결함 주입, 기존 시험 전부, 독립 검토.
6. **첫 단위는 제품 코드를 바꾸지 않는다.** 이 설계가 기대는 가정(Rust가 지금 엔진이 만드는 문자열과 오프셋을 바이트까지 똑같이 낼 수 있다)을 검사 틀만으로 먼저 확인한다. 본문 스캔, 글자 속성 조각의 다시 쓰기, zip 항목 글자 해독 셋이다.

새 크레이트는 저장소 루트의 `crates/` Cargo 워크스페이스에 둔다. 이름은 우리 것으로 짓는다(결정 0024).

## 버린 대안

- **Rust 앱을 기준으로 새 모델을 잡는다(설계안 B).** 노드마다 원본 바이트 범위와 바뀜 상태를 가진 모델, TypeScript용 투영 크레이트, 문서마다 엔진을 고르는 라우터. 끝 모습(Rust 편집기)에는 더 맞는다. 버린 까닭: 옮기는 동안 두 엔진이 실제 사용자 문서에 섞여 쓰이고, 읽은 엔진과 저장하는 엔진이 다를 때의 저장 손상 위험이 끝까지 남는다. 투영 크레이트(6,000~9,000줄 추정)가 브라우저판 때문에 영영 남는다. 일이 3분의 1쯤 더 든다(설계자 자신의 추정).
  - 이 안에서 가져온 것: 가정부터 확인하는 첫 단위, 환경마다 WASM을 스스로 찾아 싣는 로더, 빈 문서 만들기를 일찍 Rust로 넘기는 순서.
- **사이드카 프로세스나 Node 애드온으로 붙인다.** 엑셀 엔진은 사이드카다. 워드 엔진은 렌더러와 브라우저에서 같은 것을 써야 하고 호출이 잦아, 어디서나 같은 WASM 하나를 쓴다.
- **화면은 React를 두고 껍데기만 Rust(Tauri 방식).** 일이 훨씬 적고 편집기를 다시 만들지 않는다. 스풋이 화면까지 Rust로 가는 쪽을 골랐다.
- **먼저 재고 정한다.** 스풋이 물렸다.

## 알고 가는 위험

- **지금 모델은 읽은 결과의 스냅숏이다.** Rust 편집기(글자 편집, 선택, 부분 다시 그리기)는 그 위에 편집 모델이 따로 필요할 것이다. 4단계에서 모델을 다시 잡게 되면 설계안 B의 바이트 범위와 바뀜 추적이 후보다. 판정자가 이 가정이 틀리면 판정이 뒤집힌다고 적었다.
  - **재 본 것(단위 1g, 2026-11-12).** 한 run의 글자만 바꿔 저장하는 일을 두 방식으로 만들어 비교했다(`crates/spike-one-run-save`). 다른 zip 항목과 다른 문단은 두 방식 모두 바이트까지 그대로였다(저장소 문서 325번, Apache POI 시험 문서 582번 편집). 고친 문단 안의 다른 run은 달랐다. Word가 저장한 문서(POI 115개 중 98개)에서 스냅숏 방식은 가장 작은 모델로 0%, 지금 엔진이 아는 것(하이퍼링크, 책갈피, 메모 범위, 교정 표시, rsid 속성)을 모두 실어도 95.9%였고 남은 차이는 요소 사이 공백과 `xml:space` 표기였다. 바이트 범위 방식은 100%였고 코드도 적었다(249줄 대 353~429줄).
  - **읽는 법.** 스냅숏 방식의 차이는 내용 손실이 아니라 표기 차이다(같은 뜻의 XML). 엔진을 제자리에서 바꾸는 1단계의 기준은 "지금 엔진과 같은 결과"라서 이 결과로 설계안 A가 뒤집히지 않는다. 뒤집히는 것은 4단계의 편집 모델이다: run 단위로 원본을 보존해야 하는 편집기는 스냅숏 위가 아니라 바이트 범위 모델 위에 선다. 그래서 `ooxml-xml`은 지금처럼 위치를 내는 채로 두고, 4단계 설계는 바이트 범위 모델에서 시작한다.
  - **재지 않은 것.** 서식 바꾸기, run 나누기와 합치기, 문단 넣기와 지우기, 표 안의 문단. 서식 편집은 속성을 타입으로 다뤄야 해서 바이트 범위 방식의 비용이 늘 것으로 본다(추정).
- **읽기 전체를 한 번에 넘기는 단위가 길다.** 읽기(약 18,000줄)와 저장(약 12,000줄)은 안에서 서로를 불러 통째로만 넘어간다. 그 동안 TypeScript 엔진은 고치지 않는다.
- **저장소의 문서(185개)가 엔진이 하는 일을 다 덮지 못할 수 있다.** 넘기기 전에 시험 실행에서 모은 입력과 저장소 밖 실제 문서로 넓힌다.
- **화면을 다시 만드는 일이 가장 크다(약 46만 줄).** Tiptap, Univer, 한글 입력 조합을 새로 만든다. 이 결정에서 가장 오래 걸리고 가장 불확실한 부분이다.
- **원본 코드를 옮겨 적은 Rust는 파생물이다.** 라이선스 고지는 그대로 둔다(결정 0024).
- **정규식 엔진이 V8과 다르게 자란다(2026-11-12에 잼).** TypeScript 엔진은 정규식으로 XML을 읽고, Rust 쪽은 같은 패턴을 `regress`로 돌린다(`crates/jscompat`). 두 가지가 나왔다.
  - 메모리: 안에 선택(`|`)이 든 반복은 글자마다 되돌아갈 자리를 쌓고 돌려주지 않는다. 닫히지 않은 `<` 하나 뒤에 2,240만 자가 오면 wasm32 모듈이 죽는다(다음 버퍼가 4.29GB). 같은 입력에 V8은 800만 자까지 답하고 900만 자부터 0.1초 안에 `RangeError`를 낸다. zip 검사는 이런 파트를 통과시킨다(한 글자 2,200만 개는 22KB로 줄어든다).
  - 시간: 끝을 정해 주지 않은 게으른 한 글자 반복(`[\s\S]*?`)은 일치마다 글 끝까지 먼저 걸어간다. 2MB 글에서 4만 번 일치하는 한 번 훑기가 47.9초였고 Node는 4.3ms였다. 그런 패턴이 66곳이다.
  - 정한 것: `regress` 0.12.0을 `crates/vendor/regress/`에 들이고 두 군데를 고친다(되돌아갈 자리의 상한과 실패를 알리는 검색, 게으른 한 글자 반복을 한 글자씩). 상한은 2^22개(약 134MB)이고 넘으면 오류로 읽기를 거절한다. V8이 답하는 140만~800만 자 구간을 거절하게 되는 것은 받아들인 차이다. 파트 크기 상한은 두지 않는다(5MB짜리 파트는 흔하다). 이것이 풀리기 전에는 Rust 엔진을 앱에 넣지 않는다.
- **비교가 TypeScript 엔진의 결함을 계속 찾는다.** 2026-11-12까지 30건 넘게 적었다(작업 컴퓨터의 `~/.seuoffice-program/rust/ts-defects-found.md`, 입력과 두 답이 함께 있다). 규칙: TypeScript 결과가 형식 규칙에 어긋나거나 내용을 잃으면 Rust는 처음부터 옳게 쓰고, 그 입력과 두 답을 장부에 적고, TypeScript는 `main`에서 고친다. 둘 다 유효한 선택이면 그대로 따라 한다. 그래서 위의 "그 동안 TypeScript 엔진은 고치지 않는다"는 결함 수정에는 해당하지 않는다. 고친 것이 `main`에 들어오면 Rust 가지가 `main`을 받아 장부의 그 부류를 지운다.
  - 장부에 적은 부류는 그 입력의 다른 결함을 가린다. 숫자가 아닌 값(NaN)을 쓰는 부류는 입력 2,487개를 통째로 빼 두었다가, 그 값만 가리고 나머지를 비교하게 바꾸자 Rust 쪽 결함 하나가 바로 나왔다. 빼 두는 대신 가리고 비교한다.
- **결함 주입의 판정은 "차이가 늘었는가"다.** 보고서의 줄이 달라졌다고 잡은 것으로 치면, 입력이 장부의 부류로 옮겨 가기만 한 결함을 잡았다고 세게 된다(실제로 한 건 그랬다). 어떤 함수의 차이 수가 기준보다 늘어야 잡은 것이고, 수와 부류 줄만 바뀌면 놓친 것이다. 모듈이 죽어 집계가 비면 0이 아니라 실패로 센다.
- **저장소 문서만으로는 순서와 드문 경로가 드러나지 않는다.** 모델의 키 순서 68개를 "읽은 결과와 어긋나지 않는다"는 근거로 굳혔는데, 말뭉치에 없는 경로를 지나는 문서 넷을 만들자 17개가 틀렸다. 지금은 TypeScript 소스의 객체 리터럴과 대입을 읽는 분석기가 순서를 확인한다. 슬라이드 쪽은 추적 중인 덱 셋이 사용자 지정 도형, 3D 모델, 그룹을 하나도 갖지 않아 우리 내용으로 만든 덱을 더했다.
- **브라우저판의 낱말 정렬은 브라우저에 맡긴다.** TypeScript는 `localeCompare`를 쓴다. Rust에 ICU4X를 넣으면 시도한 목록에서는 같았지만(CLDR 49 대 48) 같다는 증명은 아니고, 6MB 모듈 가운데 1.5MB가 정렬 자료였다. wasm 빌드는 가져온 함수 하나로 호스트의 정렬기를 부르고, 네이티브 빌드만 ICU4X를 쓴다.
