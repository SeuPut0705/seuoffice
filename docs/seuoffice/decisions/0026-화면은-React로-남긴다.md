# 0026 화면은 React로 남긴다

- 날짜: 2026-11-12
- 상태: 확정
- 결정한 사람: 스풋("리엑트 + 러스트 이 조합이 좋나?", 문의 탭의 답을 본 뒤 "변경해봐 그럼"). 단계의 순서와 껍데기를 고르는 방법은 메인 세션이 정했다
- 결정 [0025](0025-Rust-전환.md)의 2항("화면까지 Rust로 간다")과 4단계(화면을 Rust로 다시 만들기)를 대신한다. 0025의 나머지(엔진, 중심 프로세스, Electron 제거, 브라우저판, 검사 틀)는 그대로다

## 맥락

결정 0025는 앱 전체를 Rust로 옮기고 화면도 Rust 화면 도구(GPUI 등)로 다시 만들기로 했다. 그런데 0025에 이미 적힌 사실 셋이 이 마지막 단계와 부딪힌다.

- 브라우저판(`apps/web`, 임베드)은 React와 WASM 엔진으로 남는다(0025 3항). 화면까지 Rust로 가면 같은 편집기를 React와 Rust 화면 도구로 두 벌 유지한다.
- 화면은 옮길 코드의 대부분이다(약 46만 줄: docs 14만, sheets 14만, slides 9만, pdf 8만). 0025 스스로 "가장 오래 걸리고 가장 불확실한 부분"이라 적었고, Tiptap·Univer·한글 입력 조합을 새로 만들어야 한다.
- "화면은 React를 두고 껍데기만 Rust"는 0025에서 버린 대안이었지만 버린 까닭은 스풋의 선택뿐이었다. 스풋이 이번에 그 선택을 거두었다.

## 결정

1. **화면은 지금의 React 편집기를 그대로 쓴다.** 데스크톱판과 브라우저판이 같은 화면 코드를 쓴다.
2. **단계는 셋이다.** 엔진(Rust + WASM) → 중심 프로세스(지금의 Electron main을 Rust로) → Electron 제거(Rust 껍데기가 웹 화면을 띄운다). 단계마다 `main`에는 돌아가는 앱이 남는다. 0025의 4단계는 없어진다.
3. **껍데기는 3단계를 시작할 때 재서 고른다.** 후보:
   - 시스템 웹뷰(Tauri 2: macOS WKWebView, Windows WebView2). 설치 파일과 메모리가 가장 작다. 대신 macOS에서는 화면이 Safari 엔진에서 돈다.
   - Chromium을 함께 싣는 껍데기(CEF 런타임: Tauri의 CEF 런타임이나 `cef` 크레이트). 지금 Electron과 같은 브라우저 엔진이라 화면이 바뀌지 않는다. 설치 파일과 메모리는 지금에 가깝다.
     고르는 방법: 두 후보 위에서 지금의 e2e 시험 전부와 편집기의 핵심 동작(한글 입력 조합, 복사·붙여넣기, 인쇄와 PDF 내보내기, 큰 시트, 슬라이드 그리기, PDF 보기, 공동 편집, 새 껍데기 안의 자동 업데이트, 그리고 5항의 넘어가기)을 macOS와 Windows에서 돌려, 시스템 웹뷰가 모두 같게 돌면 시스템 웹뷰, 하나라도 다르면 CEF로 간다. 5항의 넘어가기를 지키지 못하는 후보는 고르지 않는다. 결과는 새 결정으로 남긴다.
4. **지금 하는 일은 그대로 쓰인다.** Rust 엔진(워드, 슬라이드, 파일 읽기, 공용 정규식)은 1단계 그대로이고, 껍데기를 무엇으로 하든 엔진은 WASM으로 웹 화면에, 네이티브로 중심 프로세스에 붙는다.
5. **지금 Electron 판을 쓰는 사람은 평소의 자동 업데이트만으로 새 껍데기 판으로 넘어간다**(스풋, 2026-11-12: "기존 이용자도 업데이트를 통해서 알아서 변경되도록"). 다시 내려받거나 다시 설치하는 일은 없다. 그래서:
   - 넘겨 주는 판은 마지막 Electron 판이다. 그 판의 업데이터가 같은 피드(`stable.yml`, `stable-mac.yml`)에서 새 판을 받아 지금과 같은 방법으로 설치한다: Windows는 NSIS 설치 파일을 실행하고(`--updated`), Mac은 우리 업데이터가 zip을 앱 옆에 풀어 이름을 바꿔 끼운다(`apps/shell/src/main/mac-update.ts`, 바꿔 끼우기에 실패하면 옛 앱을 되돌려 연다). 그러므로 새 판도 이 두 형식(Windows NSIS 설치 파일, Mac 앱 묶음 zip)으로 나오고, 첫 새 판의 업데이터는 같은 피드를 계속 읽는다.
   - 그대로 지킬 것: 설치된 앱의 정체(결정 0013, 0019: 앱 이름, appId와 Mac bundle id, Windows의 사용자별 설치 위치 `%LOCALAPPDATA%\Programs\SeuOffice`와 프로그램 등록(제거 정보 키), 파일 연결의 ProgId, 시작 메뉴·바탕화면 바로가기, 명령줄 연결), 사용자 자료 폴더(`%APPDATA%\seuoffice`, `~/Library/Application Support/seuoffice`)와 그 안의 파일 형식(설정, 최근 목록, 프로젝트와 대화, 복구본, 세션 기록), 저장된 비밀값. 비밀값(AI 키, 드라이브·MCP 토큰)은 지금 Electron의 `safeStorage`로 암호화되어 있다(`ai-secrets.ts`, `drive-vault.ts`, `mcp-client/secrets.ts`): 그 열쇠는 Mac 키체인의 항목과 Windows의 DPAPI로 보호된 값이라, 새 껍데기가 같은 열쇠로 풀 수 있어야 한다. 풀 수 없으면 넘어가기 전 판(마지막 Electron 판)이 비밀값을 새 판이 읽는 형식으로 옮겨 적는다.
   - 넘어가다 실패하면 옛 판이 그대로 돈다(설치 파일이 끝나지 않거나 새 판이 뜨지 않으면 옛 판으로 돌아간다). 한 번에 넘어가지 못한 사람은 다음 확인에서 다시 시도된다.
   - 시험(껍데기를 고르는 시험과 넘겨 주는 판을 낼 때 둘 다): Mac과 Windows 실기기에서, 그동안 낸 Electron 판 가운데 오래된 판과 마지막 판 각각에 설정·최근 목록·프로젝트 대화·AI 키·복구본을 만들어 두고 앱 안 업데이트만으로 새 판에 이르러, 모두 그대로인지와 다시 업데이트되는지를 본다. 실패를 일부러 일으켜(설치 도중 끄기, 새 판이 뜨지 않게 하기) 옛 판이 돌아오는지도 본다.

## 버린 대안

- **화면까지 Rust(GPUI 등).** 메모리와 속도에서 가장 크게 얻는다. 버린 까닭: 편집기를 두 벌(Rust 화면, 브라우저판 React) 유지해야 하고, 46만 줄을 다시 만드는 가장 긴 단계이며, 화면 도구가 아직 1.0 전이다.
- **Electron을 그대로 두고 엔진만 Rust.** 일이 가장 적다. 버린 까닭: 스풋이 원한 "가볍고 빠른 고유 앱"에서 Node 중심 프로세스의 무게가 남는다. 2단계와 3단계를 하지 않을 까닭이 없다.

## 결과

- 메모리 절감은 주로 Node 중심 프로세스와 Electron 런타임이 빠지는 만큼이다. 화면은 여전히 브라우저 엔진이 그린다. 시스템 웹뷰를 고르면 더 줄고, CEF를 고르면 지금과 비슷하다.
- 화면 코드는 계속 TypeScript다. 결정 0024의 "앱 언어 영어·한국어" 축소는 그대로 유효하고, 화면 문구를 옮길 일은 없어진다.
- 브라우저판에서 Chromium 외 브라우저 확인(지금 막혀 있음)이 시스템 웹뷰를 고를 때의 확인과 겹친다. 3단계에서 함께 한다.
