# 0027 판은 모아서 낸다

- 날짜: 2026-11-12
- 상태: 확정
- 결정한 사람: 스풋("한번에 진행하라고, 빌드할때마다 시간 잡아먹는데 그걸 여러번 하고있으니"), 방식은 메인 세션
- 바꾸는 결정: [0020](0020-main-푸시마다-미리보기-판.md)의 "main 푸시마다 판을 낸다"

## 맥락

0020에 따라 main 푸시마다 판이 나왔다. 2026-11-12 하루에 0.12.29부터 0.12.35까지 일곱 판이 나왔다. 판마다 두 가지 비용이 든다.

- 릴리스 빌드: Windows와 Mac 설치 파일을 채널마다 두 번 묶고 웹 묶음을 만든다. 실행 하나가 러너에서 10분 넘게 돈다(0020의 잰 값: mac 8.5분, windows 10.5분).
- 사용자: 판마다 업데이트를 받아 설치를 기다린다. 스풋의 Windows PC에서 '다시 시작 및 설치'부터 앱이 다시 뜰 때까지 141~179초였다.

## 결정

- **main 푸시는 판을 만들지 않는다.** `.github/workflows/seuoffice-desktop.yml`은 main 푸시에 돌지 않는다. `CI`와 `seuoffice` 검사는 지금처럼 푸시마다 돈다.
- **판은 모아서 사람이 시작한다.** 합친 변경이 한 묶음이 되면 메인 세션이 `gh workflow run "seuoffice desktop release" --ref main -f release=true`로 판을 낸다. 판 번호를 고르는 법, CI와 seuoffice 녹색을 기다리는 것, 미리보기 판으로 내는 것은 0020과 같다. `v*` 태그를 손으로 미는 길도 그대로다.
- **언제 내는가.** 진행 중인 묶음(같이 검사 중인 가지들)이 다 합쳐진 뒤에 낸다. 횟수 상한은 두지 않는다(2026-11-13 바로잡음: 처음에 적은 '하루에 많아야 한 번'은 스풋이 말한 적 없는 숫자였다). Rust 단위 일만으로는 내지 않는다. 사용자에게 보이는 변화가 없는 커밋(문서, 시험, 개발 도구, Rust 비교 기록)만 쌓였으면 내지 않는다.
- **기다리지 않는 것.** 보안 결함, 문서를 잃거나 망가뜨리는 결함, 앱이 켜지지 않거나 업데이트가 안 되는 결함은 고친 즉시 판을 낸다.
- **안정 판으로 올리는 것은 그대로다.** 미리보기 판이 나오면 확인 뒤 `gh release edit vX.Y.Z --prerelease=false --latest`로 올린다.

## 버린 대안

- **정해진 때(예: 매일 밤)에 자동으로 내기.** 바뀐 것이 없거나 검사 중인 가지가 반만 합쳐진 날에도 판이 나온다. 묶음이 끝나는 때를 아는 것은 메인 세션이다.
- **main 푸시마다 빌드는 하고 게시만 모으기.** 빌드 시간 낭비가 그대로 남는다.

## 결과

- 릴리스 빌드는 판을 낼 때만 돈다. 사용자는 묶음마다 한 번 업데이트를 받는다.
- 커밋이 일반 채널 설치본에 닿기까지 사람이 판을 시작할 때까지 기다린다. 0020이 줄인 시간(약 31분)은 급한 수정에만 남는다.
- main 머리가 문서만 바꾼 커밋이면 푸시로는 CI가 돌지 않는다. 그때는 `gh workflow run CI --ref main`으로 손으로 돌리고, 릴리스 작업은 손으로 돈 실행도 그 커밋의 CI로 받는다.
