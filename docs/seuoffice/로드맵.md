- 상태: 완료(2026-11-10). 공개 전 검사를 마치고 2026-11-08에 공개로 바꿨다. 이력에서 로컬 경로와 개인 메일을 지우려고 우리 커밋 29개를 고쳐 썼다(이음 `aea1414`까지는 그대로). gitleaks로 이력을 검사해 15건이 나왔는데 모두 상위 시험용 가짜 키였다. 웹 묶음은 npm 대신 앱 릴리스에 `seuoffice-embed-<판>.tgz`(16kB)와 `seuoffice-web-<판>.tgz`(59.6MB)로 붙고, 붙이는 쪽은 릴리스 주소로 설치한다(결정 0021, `판-내기.md`). npm 조직·계정·토큰이 필요 없다.

## 2단계: 웹 편집과 저장

- 앱별 저장 브리지: docx 생성·패치를 브라우저에서, xlsx `save_archive` wasm, pptx 저장 바이트, hwp `exportHwp*` + `applySaveFixes`를 브라우저에서, pdf는 pdf-lib 단계 먼저(pdfium wasm 단계는 나중에).
- embed 저장 메시지: `{type:'save', fileName, bytes}` → 호스트가 받아 저장하고 응답한다.
- 단일 편집자 잠금: 호스트(유유)가 잠금을 잡은 경우에만 `mode=edit`로 연다. 잠금을 못 얻으면 읽기 모드. 동시 편집은 하지 않는다.
- 암호 문서(pdf RC4·MD5 JS 구현, docx officecrypto 브라우저 확인).
- 완료 조건: 한글 왕복 측정에서 알려진 손실 외 불일치 0, 한컴 한글 수동 재열기 확인.
- 상태: 완료(2026-11-09). 다섯 형식 모두 편집 모드에서 같은 형식으로 호스트에 저장되고, 보기 모드에서는 고칠 수 없다. 사람 몫인 한컴 한글 재열기 확인만 남았다.
  - embed 편집·저장 계약(U0): `mode: 'edit'`, `onSave`, `onDirtyChange`, `save()`. 호스트는 한 문서의 저장을 도착 순서대로 하나씩 처리한다.
  - 한글(U4): 편집 모드에서 hwp/hwpx를 같은 형식으로 저장해 호스트에 넘긴다. 앱 저장(Ctrl+S, 파일 메뉴)과 호스트 요청 저장 모두 데스크톱과 같은 보정(`applySaveFixes`)을 거친다. 왕복 측정이 웹 경로도 함께 확인한다(37개, 불일치 0). 웹 시험 `save-hwp.spec.ts` 3건. 보기 모드와 모드 없음은 읽기 전용 편집기로 연다(결정 0016, U4b). studio에 읽기 전용 모드가 없어 빌드 패치 셋(명령, 편집 연산, 엔진 문서)으로 막고, 보기 모드 시험이 글 치기·입력기 글·지우기·붙이기·서식 뒤에도 문서와 저장 안 됨 상태가 그대로인지 본다.
  - PDF(U8): pdf-lib으로 쓰는 편집(주석, 양식, 페이지 회전·삭제·순서, 메타데이터, 책갈피, 첨부)을 편집 모드에서 호스트로 저장한다. 텍스트·이미지 편집, 저장된 주석 삭제, 영구 제거는 웹에서 저장을 거절한다(결정 0010). 보기 모드는 읽기 전용이다. 웹 시험 `save-pdf.spec.ts` 4건.
  - 암호 문서(U10): 웹에서 암호 PDF(RC4, AES-128, AES-256, 소유자 암호만 있는 파일)와 암호 docx(Agile, Standard)를 앱의 암호 창으로 연다. 틀린 암호는 앱의 기존 오류를 보인다. 편집 모드 저장은 같은 암호로 다시 잠그고, PDF "보호"와 docx "문서 보호"의 암호 설정·해제도 다음 저장부터 적용된다. 데스크톱 암호 모듈을 그대로 들이고 웹 `crypto` 대체 모듈에 AES를 더했다(결정 0015). 웹 시험 `encrypted.spec.ts` 12건.
  - 워드(U5): 편집 모드에서 앱 저장(버튼, Ctrl+S)과 호스트 저장 요청이 docx 바이트를 `saveToHost`로 넘긴다. 바이트는 원래 렌더러가 `@seuoffice/docx-engine`으로 만들고, 메인 프로세스는 지연 그림 채우기·암호화·디스크 쓰기만 해서 엔진을 옮길 필요가 없었다. 보기 모드는 읽기 모드를 끌 수 없게 잠갔다(전에는 Esc로 편집이 됐다). 웹 시험 `save-docs.spec.ts` 5건.
  - 웹 글꼴(U9): 디자인 템플릿 글꼴을 웹 묶음 `template-fonts/`에 한 번 싣고 docs·sheets는 데스크톱 등록 코드를 그대로 쓴다. slides는 덱이 이름을 대는 패밀리만 받는다. hwp 스튜디오에 옛한글 글꼴을 넣었다(결정 0011, 웹 묶음 +51.4MiB). hwp PC 글꼴 목록과 slides 시스템 글꼴은 남는다. 웹 시험 `fonts.spec.ts` 5건.
  - 파워포인트(U6): 편집 모드에서 글 고치기, 슬라이드 추가·삭제, 노트, 되돌리기·다시하기가 페이지 안 세션에서 데스크톱과 같은 트랜잭션 코드로 돈다. 저장(Ctrl/Cmd+S, 저장 단추, 호스트 `save()`)은 `savePptx` 바이트를 호스트에 넘긴다. 나머지 편집 연산은 `web-gaps.md`에 남겼다. 웹 시험 `save-slides.spec.ts` 5건. 저장 시점을 넘어 되돌리면 덱을 저장된 것으로 보는 문제를 웹만 고쳤다. 데스크톱도 같은 동작이라고 코드로 판단했고(실행 확인 안 함), 닫을 때 변경을 잃을 수 있어 상위에 알리거나 고칠 일로 남긴다.
  - 엑셀(U7): 편집 모드에서 wasm 엔진 워커가 게이트웨이로 저장을 계획하고 엔진 `save_archive`로 써서 호스트에 넘긴다. 손대지 않은 부분은 원본과 바이트까지 같다. 보기 모드는 셀 편집 명령, Univer 변경, 리본·오른쪽 단추 허용 목록, 그림 붙여넣기 네 겹으로 막는다(결정 0014). 웹 시험 `save-xlsx.spec.ts`. 엑셀 암호 통합 문서는 웹에서 아직 열지 못한다(`web-gaps.md`).
  - 남은 것: 한컴 한글 재열기(사람 몫).

## 3단계: AI 게이트웨이와 변경 추적

- `packages/ai-provider`에 `gateway-complete` 프로토콜을 추가한다(`AiProtocol`, `AI_PROVIDER_ADAPTERS`, `chat.ts`·`stream.ts` 분기, `protocols/gateway-complete.ts`). 요청마다 부른 사람 토큰을 메모리로만 넘기고 설정 파일에 저장하지 않는다. 웹에서는 호스트가 게이트웨이를 부르게 한다.
- AI 편집 추적 강제: docs `ai/tools.ts`에서 `accept_changes`·`reject_changes`를 빼고, `ai/ops.ts`에서 AI 편집 추적을 항상 켠다.
- hwp·sheets·slides는 앱별 조사 뒤 "제안 → 미리보기 → 사람 수락"으로 한다.
- 상태: 완료(웹 AI 포함). 게이트웨이와 docs AI 편집 추적 강제는 끝냈다(결정 0009). `gateway-complete`는 OpenAI Chat Completions 요청과 SSE 모양을 그대로 쓰고, 토큰은 요청마다 공급자(`setGatewayTokenProvider`)에게 받아 머리글에만 싣는다. docs에서 AI 편집은 사용자 토글과 상관없이 `AI Assistant` 작성자의 변경 추적으로 남고, AI는 변경을 받아들이거나 거절할 수 없다. hwp·sheets·slides의 AI 편집은 실행하는 동안 문서가 잠기고 저장이 막히며, 끝나면 앱의 되돌리기로 빼서 제안이 되고, 사람이 받아들여야 들어간다(결정 0012). 이 단위는 다른 모델로 세 번 독립 검토했고, 받아들이지 않은 AI 편집이 남는 길 4개를 찾아 막았다. 웹에서는 페이지가 AI 한 턴의 `gateway-complete` 요청 본문을 embed 통로(`ai_request`)로 호스트에 넘기고, 호스트가 자기 토큰으로 게이트웨이를 불러 SSE 바이트와 `Content-Type`·`Retry-After`를 돌려준다(`ai_chunk`·`ai_end`·`ai_error`, 취소 `ai_cancel`, 결정 0017). docs, hwp, sheets, pdf의 웹 브리지가 데스크톱 프로토콜 코드를 그대로 돌리고, docs AI 편집은 웹에서도 `AI Assistant` 변경 추적, sheets AI 편집은 제안으로 남는다(웹 시험 `ai-relay.spec.ts`). slides도 웹에서 AI 실행을 제안으로 붙잡는다(결정 0018, 웹 시험으로 확인). 웹에서 되는 slides AI 편집 도구는 `apply_ops` 하나다. hwp 웹 AI도 같은 시험으로 제안·받아들이기·저장을 확인했다. 남은 일(3단계를 막지 않음): docs MCP 다리(`mcp-bridge.ts`)와 CLI `docs apply`의 추적, 한글 거부 뒤 사람 다시 실행 막힘(결정 0012 남은 일), Electron 화면에서 눈으로 확인.

## 4단계: 앱 배포(Apple Silicon Mac, Windows)

- 앱 릴리스는 Apple Silicon Mac(arm64)과 Windows(x64) 두 가지만 낸다(스풋 결정, 2026-11-09). Linux와 Intel Mac은 빌드하지 않는다.
- `productName`·`appId`·창 제목 seuoffice(`apps/shell/package.json`, `electron-builder.cjs` :532–533, `packages/i18n` 제품명).
- 업데이트 피드: 저장소를 공개하면 GitHub 릴리스 피드를 쓸 수 있다. 유유용 안정 판 채널을 일반 채널과 따로 둔다(결정 0007).
- 코드 서명: 스풋이 서명 없이 운영하기로 정했다(2026-11-09, 결정 0013). 서명된 판이 한 번 나가면 그 뒤로는 서명 없는 판으로 업데이트되지 않으므로(`docs/archive/ieum/releasing.ko.md` 서명 주의), 나중에 서명으로 바꾸면 되돌아오지 않는다. 서명은 비밀값만 넣으면 워크플로가 한다.
- 상태: 완료(2026-11-09). 사용자에게 보이는 이름이 seuoffice(appId `com.seuput.seuoffice`)이고, 업데이트 피드는 `SeuPut0705/seuoffice` GitHub 릴리스다. 채널은 `latest`·`stable` 두 가지로 빌드할 때 정한다(`SEUOFFICE_UPDATE_CHANNEL`). `apps/shell/electron-builder.seuoffice.cjs`가 대상을 Mac arm64(dmg, zip)와 Windows x64(NSIS)로 묶고 다른 대상은 거부한다. `.github/workflows/seuoffice-desktop.yml`이 `v<판 번호>` 태그에서 두 플랫폼을 빌드하고, 릴리스를 만든다(결정 0013). 스풋이 서명 없이 운영하기로 정해(2026-11-09) 서명이 없어도 판을 내고, 본문에 Windows SmartScreen·Mac Gatekeeper 안내를 적는다. 자동 업데이트는 서명 없이도 돈다. npm 묶음 태그는 `npm-v<판 번호>`로 옮겼다. 첫 릴리스 [v0.12.11](https://github.com/SeuPut0705/seuoffice/releases/tag/v0.12.11)을 서명 없이 미리보기(latest 채널)로 냈다(워크플로 실행 42559082328: Mac dmg·zip, Windows 설치 파일, 두 채널 피드 파일). 안정 채널로 올리는 것은 스풋이 설치해 본 뒤 `gh release edit v0.12.11 --prerelease=false --latest`로 한다. [v0.12.12](https://github.com/SeuPut0705/seuoffice/releases/tag/v0.12.12)는 SeuOffice 이름과 카드 아이콘이 든 첫 판이고 안정 채널로 올렸다(워크플로 실행 42595497496). README 다운로드 단추는 이 판의 판 번호 없는 사본을 받는다. main 푸시마다 CI와 seuoffice가 녹색이면 다음 판을 일반 채널 미리보기로 자동으로 내고, 안정 채널은 스풋이 올린다(결정 0020). 0.12.12부터 판 번호는 우리가 올린다(SeuOffice 이름과 카드 아이콘이 든 첫 판, 안정 채널로 올려 README 다운로드 단추가 받는다). 이음을 따라잡을 때 `apps/shell/package.json` 판은 둘 중 큰 쪽을 두고 그다음 판으로 낸다.

## 5단계: 동시 편집

- 동시 편집을 설계한다. 공개 여부는 1.5단계에서 정했다(결정 0007).
- 상태: 완료(2026-11-09). 결정 0008: 실시간 공동 편집은 하지 않고, 붙이는 쪽이 잠금·판 검사·넘겨주기를 맡는다. seuoffice 쪽은 2단계 저장 계약으로 충분하다. 실시간 편집은 결정에 적은 조건이 생기면 다시 연다.

## 6단계: 실시간 공동 편집

- 여러 사람이 같은 문서를 같은 순간에 고친다. 가운데 서버 하나가 편집 순서를 정하고, 공통 클라이언트 하나에 편집기마다 어댑터를 꽂는다(결정 0023, 0008의 1번을 뒤집음).
- 순서: 공통 부품(`@seuoffice/collab`: 서버, 클라이언트 엔진, 적합성 시험) → 붙이는 쪽 통로(embed, web-platform) → 형식별 어댑터. 한글은 잠금으로 둔다.
- 완료 조건: 브라우저 두 개가 같은 문서를 열어 서로의 편집을 보고, 어느 쪽이 저장해도 두 사람 편집이 모두 든 파일이 나온다. `collab` 옵션 없이 연 문서는 지금과 같다.
- 상태: 첫 판을 냈다(2026-11-11). 시험 단계다. 워드, 엑셀, 파워포인트, PDF 어댑터가 있고 한글은 잠금이다. 완료 조건은 형식마다 브라우저 두 개 시험으로 확인했다. 실제 붙이는 쪽, 오래 가는 저장소, 실제 네트워크에서는 써 보지 않았다. 확인한 것과 아닌 것, 붙이는 쪽이 할 일은 [`공동-편집.md`](공동-편집.md)에 있다.
- 남은 일: 붙이는 쪽(유유) 통합과 그쪽 저장소·인증, 사본 문서로 써 보기, Chromium 밖 브라우저, 긴 묶음과 부하. 그 결과를 보고 시험 단계를 뗀다.

## 7단계: 원본과 갈라서기

- 이음오피스와 GenOffice를 마지막으로 한 번 따라잡고, 그 뒤로는 상위를 따라가지 않는다(결정 0024, 0002와 0006을 뒤집음).
- 순서: 이음 merge(2026-11-11까지) → GenOffice에서 이음이 받지 않은 커밋 옮기기 → 릴리스 → 원격·규칙·도구·연락처 정리, 상위 기록 문서는 `docs/archive/`로 → 내부 이름 바꾸기(옛 설정 폴더와 문서 네임스페이스는 계속 읽음) → 릴리스.
- 라이선스 고지(`LICENSE`, `NOTICE`, 제3자 고지, `upstream-edits.md`)는 그대로 둔다. git 이력은 고쳐 쓰지 않는다.
- 완료 조건: 저장소에 상위를 따라가기 위한 원격·규칙·도구가 없고, 내부 이름이 우리 것이며, 이름을 바꾼 판이 옛 판의 설정과 문서를 그대로 연다.
- 상태: 진행 중. 이음 merge와 GenOffice 따라잡기를 끝내고 v0.12.29(2026-11-12)로 냈다. 원본 정책 문서와 앱 안의 원본 연락처·사이트 링크를 지웠고, 상위를 따라가던 도구와 워크플로를 없앴고, 이음오피스의 기록 문서를 `docs/archive/ieum/`으로 옮겼다(v0.12.32). 남은 것: 앱 언어를 영어·한국어로 줄이기, 원격 삭제와 루트 규칙의 "상위 따라가기" 절, 내부 이름 바꾸기, 그 판의 릴리스와 Windows 확인.

## 8단계: Rust 전환

- 앱의 중심을 Electron과 TypeScript에서 Rust로 옮긴다(결정 0025). 화면은 지금의 React 편집기를 그대로 쓴다(결정 0026이 0025의 "화면까지 Rust"를 대신함). 순서: 문서 엔진(워드부터) → 중심 프로세스 → Electron 제거(Rust 껍데기가 웹 화면을 띄운다). 단계마다 `main`에는 돌아가는 앱이 남는다.
- 껍데기는 3단계를 시작할 때 시스템 웹뷰(Tauri 2)와 Chromium을 싣는 껍데기(CEF) 위에서 e2e 시험과 편집기의 핵심 동작을 macOS·Windows에서 돌려 고른다.
- 지금 Electron 판을 쓰는 사람은 앱 안 자동 업데이트만으로 새 껍데기 판으로 넘어간다(결정 0026 5항: 같은 피드, 같은 설치 형식, 같은 앱 정체와 자료 폴더, 저장된 비밀값 유지, 실패하면 옛 판). 이 넘어가기를 지키지 못하는 껍데기는 고르지 않는다.
- 브라우저판은 React와 WASM 엔진으로 남는다. 엔진은 네이티브와 `wasm32-wasip1` 둘 다로 빌드한다.
- 워드 엔진은 지금 모델을 그대로 내는 Rust 엔진으로 제자리에서 바꾼다. 단위마다 TypeScript 엔진과 결과를 맞대는 검사를 통과해야 넘어간다.
- 상태: 1단계(엔진) 진행 중. 워드, 슬라이드, 파일 읽기의 Rust 엔진을 가지에서 만들고 있다(제품에는 아직 넣지 않음). 파일 읽기(`@seuoffice/file-parse`)는 가지 `feat/rust-fileparse-d3`에서 Rust 엔진으로 바꿔 끼웠다(D3): 내보낸 이름과 형은 그대로, TypeScript 읽기는 지웠고, 호스트에는 파일 읽기, PDF·지도·ODT 읽기(기다리는 읽기), parse5·draw.io 단계만 남는다. 비교가 찾은 TypeScript 엔진 결함은 `main`에서 고친다. Rust 엔진을 앱에 넣기 전에 풀 일: 정규식 엔진의 메모리·시간 상한(풀었고 가지에 있음), 모든 TypeScript 결함 수정이 `main`에 들어간 뒤의 비교.
