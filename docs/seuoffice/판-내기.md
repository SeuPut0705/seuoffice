# 판 내기

seuoffice 웹 묶음을 npm에 판 번호를 붙여 내는 방법. 결정 0007에 따라 유유헬스케어는 이 판을 고정해 받아 쓴다.

## 내는 것

| 패키지             | 내용                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| `@seuoffice/embed` | 호스트 쪽 라이브러리(`openDocument`). 빌드한 ESM JS와 `.d.ts`                           |
| `@seuoffice/web`   | 빌드한 정적 웹 묶음(`dist/`). 호스트가 한 주소 아래 그대로 서빙한다. 코드 의존성은 없다 |

두 패키지는 항상 같은 판 번호를 쓴다. 판 번호는 `0.1.0`에서 시작하고 semver를 따른다. `@seuoffice/web-platform`은 웹 묶음 안에 들어가는 내부 부품이라 내지 않는다.

저장소 안에서는 `@seuoffice/embed`가 소스(`src/index.ts`)로 풀린다. `package.json`의 `exports`에 `seuoffice-source` 조건을 두었고, `apps/web`의 `tsconfig.json`(`customConditions`)과 `vite.config.ts`(`resolve.conditions`)가 그 조건을 켠다. 그래서 `dist`를 먼저 빌드하지 않아도 타입검사와 웹 빌드가 돈다. 외부 소비자는 그 조건을 모르므로 `dist`를 받는다.

## 판 내는 순서

1. `main`이 CI(`CI`, `seuoffice`) 통과 상태인지 확인한다.
2. 두 패키지 판 번호를 한꺼번에 올린다.

   ```sh
   node scripts/seuoffice-release.mjs bump 0.2.0
   npm install --package-lock-only --ignore-scripts
   ```

   `npm version 0.2.0 -w @seuoffice/embed -w @seuoffice/web --no-git-tag-version`도 같은 일을 하지만, 두 판 번호가 어긋나지 않게 위 스크립트를 쓴다.

3. 커밋하고 태그를 단다. 태그는 `v<판 번호>`다.

   ```sh
   git commit -am "chore: release 0.2.0"
   git tag v0.2.0
   git push origin main v0.2.0
   ```

4. 태그가 올라가면 `.github/workflows/seuoffice-release.yml`이 돈다.
   - 태그와 두 패키지 판 번호가 다르면 첫 단계에서 실패한다. 이때는 태그를 지우고(`git push origin :refs/tags/v0.2.0`) 판 번호를 바로잡아 다시 단다.
   - 통과하면 embed 타입검사와 시험, 웹 묶음 빌드를 거쳐 `npm publish --provenance --access public`으로 두 패키지를 낸다.
5. npmjs.com에서 두 패키지의 새 판과 출처 증명(provenance) 표시를 확인한다.

이미 낸 판 번호는 다시 낼 수 없다. 잘못 낸 판은 고쳐서 다음 번호로 낸다(`npm deprecate`로 표시만 한다).

## 내기 전에 손으로 확인하기

```sh
npm run build -w @seuoffice/web
npm publish --dry-run -w @seuoffice/embed
npm publish --dry-run -w @seuoffice/web
```

- embed 파일 목록은 `LICENSE`, `NOTICE`, `README.md`, `dist/index.js`, `dist/index.d.ts`, `package.json`뿐이어야 한다.
- web은 `dist/` 아래 파일과 `LICENSE`, `NOTICE`, `README.md`, `package.json`뿐이어야 한다. `dist/index.html`이 없으면 `prepack`이 막는다(먼저 `npm run build -w @seuoffice/web`).
- `LICENSE`와 `NOTICE`는 `scripts/seuoffice-prepack.mjs`가 저장소 루트에서 복사한다. 복사본은 git이 무시한다.

## 유유헬스케어가 받는 법

유유는 `^`나 `~` 없이 정확한 판 번호로 고정한다. 두 패키지를 같은 번호로 둔다.

```json
{
  "dependencies": {
    "@seuoffice/embed": "0.1.0",
    "@seuoffice/web": "0.1.0"
  }
}
```

`@seuoffice/web`의 `dist/`는 유유 빌드 과정에서 정적 경로(예: `public/seuoffice/`)로 복사해 서빙하고, 그 주소를 `openDocument`의 `baseUrl`로 넘긴다. 서빙하는 웹 묶음과 호스트 코드가 다른 판이 되면 안 되므로 두 번호를 같이 올린다.

### 판 올리기

1. 유유 저장소에 `chore(seuoffice): 0.1.0 -> 0.2.0` 같은 판 올리기 커밋을 만든다. 이 커밋은 `package.json`의 두 판 번호, 잠금 파일, 복사해 둔 웹 묶음만 바꾼다. 다른 변경을 섞지 않는다.
2. seuoffice 저장소 `docs/seuoffice/`의 로드맵과 변경 내용에서 그 판이 바꾼 동작을 읽고, 유유가 쓰는 쪽(열기, 편집 잠금, 저장 처리)에 영향이 있는지 본다.
3. 배포 전 검사를 돌린다. 유유가 쓰는 형식(docx, xlsx, pptx, pdf, hwp, hwpx)의 모의 문서를 열고, 편집 모드로 고쳐 저장한 바이트가 호스트에 저장되는지 확인한다. 실데이터는 쓰지 않는다.
4. 검사가 통과하면 운영에 넣는다. 문제가 있으면 판 올리기 커밋만 되돌린다.

## 소유자가 한 번만 하는 설정 (npmjs.com)

긴 수명 토큰은 만들지 않는다. npm 신뢰 게시자(trusted publisher)로 GitHub Actions가 직접 인증받는다.

1. npmjs.com에서 조직 `seuoffice`를 만든다(Organizations, Create). 공개 패키지만 내므로 무료 조직이면 된다.
2. 처음 한 번은 패키지가 npm에 없으므로 신뢰 게시자를 걸 수 없다. 두 가지 중 하나로 처음 판을 만든다.
   - 소유자가 로컬에서 `npm login` 뒤 `npm publish --access public --provenance=false -w @seuoffice/embed -w @seuoffice/web`으로 첫 판을 낸다. 두 패키지의 `publishConfig`에 `provenance: true`가 있어서 `--provenance=false`를 빼면 로컬 게시는 출처 증명 오류로 실패한다. 이 첫 판에는 출처 증명이 붙지 않는다.
   - 또는 npm이 지원하는 경우 패키지를 만들기 전에 신뢰 게시자를 먼저 등록한다(npm 문서의 현재 절차를 따른다).
   - 어느 쪽이든 첫 판 번호는 `0.1.0`이다. 이미 낸 번호는 다시 낼 수 없으므로, 태그로 도는 첫 CI 게시는 그다음 번호(예: `0.1.1`)부터 한다. 신뢰 게시자는 첫 판을 낸 뒤 3번에서 등록한다.
3. 두 패키지 각각의 Settings, Trusted Publisher에서 GitHub Actions를 고르고 다음을 넣는다.
   - Organization or user: `SeuPut0705`
   - Repository: `seuoffice`
   - Workflow filename: `seuoffice-release.yml`
   - Environment: 비워 둔다
4. 두 패키지의 게시 접근을 "신뢰 게시자로만"(토큰 게시 금지)으로 좁히는 것을 권장한다.
5. 저장소가 공개 전환된 뒤에야 출처 증명이 붙는다(공개 전환은 `AGENTS.md` 경계 3에 따라 스풋이 확인한 뒤 한다). 비공개 저장소에서는 `--provenance` 게시가 실패한다.

설정이 끝나면 위 "판 내는 순서"만 따르면 된다. 워크플로에는 `id-token: write` 권한만 있고 비밀값은 없다.
