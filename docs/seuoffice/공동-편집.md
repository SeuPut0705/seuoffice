# 실시간 공동 편집

여러 사람이 같은 문서를 같은 순간에 고친다. 붙이는 쪽(호스트)이 `collab` 옵션으로 열 때만 켜지고, 옵션 없이 연 문서와 데스크톱 앱은 전과 같다. 방향과 버린 대안은 [결정 0023](decisions/0023-실시간-공동-편집.md)에 있다.

## 한눈에

- 가운데 서버(`@seuoffice/collab/server`)가 편집 순서를 정한다. 문서마다 변경 기록 하나를 두고, 변경은 최신 판 위에서 만든 것일 때만 붙는다. 서버는 변경 내용을 읽지 않는다.
- 편집기 iframe 안의 엔진(`@seuoffice/collab/client`)이 "확정된 상태 + 아직 확정 안 된 내 편집"을 들고, 밀리면 내 편집을 남의 편집 위로 옮겨 다시 보낸다.
- 편집기마다 어댑터 하나가 "옮기는 방법"을 구현한다(`apps/<앱>/src/web/collab-*.ts`).
- 주소와 토큰은 붙이는 쪽 페이지가 가진다. iframe은 embed 통로로만 서버에 닿는다.

| ---- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| docx | 본문 전부(글, 표, 그림, 변경 추적), 메모, 각주·미주, 목록 정의, 스타일, 구역 쪽 설정, 머리글·바닥글, 워터마크 | 열기 암호 바꾸기, 한 번에 8 MiB를 넘는 편집                                                                                   |

같은 것을 두 사람이 동시에 고치면 서버가 나중에 받은 쪽이 이긴다. 문서 본문만 글자 단위로 합쳐진다. 시트의 같은 셀, 슬라이드의 같은 글상자, PDF의 같은 주석은 한쪽 것만 남는다.

스트리밍으로 여는 큰 통합 문서와 어댑터가 없는 형식은 페이지가 `collab_unavailable`로 거절한다. 붙이는 쪽은 그때 `collab` 없이 잠금을 잡고 다시 연다.

## 붙이는 쪽이 할 일

### 화면

```ts
import { openDocument, SeuofficeEmbedError } from '@seuoffice/embed'

const doc = openDocument(container, {
  baseUrl,
  bytes, // 붙이는 쪽이 마지막으로 저장한 파일
  fileName,
  mode: canEdit ? 'edit' : 'view',
  collab: {
    // 처음 열 때와 다시 이을 때마다 불린다. 아직 열리지 않은 소켓을 돌려준다
    connect: async () => new WebSocket(await collabUrlWithTicket(docId)),
    onStatus: (status) => showPeers(status),
  },
  onSave: async ({ bytes, fileName, version }) => {
    // 반드시: 이미 저장한 판보다 낮은 version은 throw로 거절한다
    await store.putIfNewer(docId, { bytes, fileName, version })
  },
})

try {
  await doc.opened
} catch (error) {
  if (error instanceof SeuofficeEmbedError && error.code === 'collab_unavailable') {
    doc.destroy()
    // 잠금을 잡고 collab 없이 다시 연다
  }
}
```

### 서버

```ts
import { WebSocketServer } from 'ws'
import { createCollabServer, memoryStore } from '@seuoffice/collab/server'

const collab = createCollabServer({ store: memoryStore() })

new WebSocketServer({ server, maxPayload: 50 * 1024 * 1024 }).on('connection', (ws, request) => {
  const principal = verifyTicket(request) // 붙이는 쪽의 인증: { documentId, userId, name, canEdit }
  if (!principal) return ws.close()
  collab.accept(toServerSocket(ws), principal)
})
```

`toServerSocket`은 `packages/collab/README.md`에 예가 있다.

### 꼭 지킬 것

1. **인증은 붙이는 쪽이 한다.** 서버는 `accept`에 넘어온 `Principal`을 믿는다. `canEdit: false`인 사람은 편집을 보낼 수 없다.
2. **낮은 판으로 덮어쓰지 않는다.** `onSave`가 받은 `version`이 저장해 둔 것보다 낮으면 throw한다. 지키지 않으면 늦게 도착한 옛 저장이 새 저장을 덮고, 다음 사람이 그 파일에서 시작해 그 사이 편집을 잃는다.
3. **공동 편집 밖에서 파일을 바꿨으면 `collab.reset(documentId)`를 부른다.** 새 판 올리기, 데스크톱에서 고친 파일 올리기가 그렇다.
4. **오래 가는 저장소는 붙이는 쪽이 만든다.** 실려 있는 것은 메모리 저장소(`memoryStore`)뿐이라 서버를 다시 띄우면 저장 안 된 편집이 사라진다. `CollabStore` 인터페이스를 자기 DB에 맞춰 구현한다. `append`는 원자적이어야 한다(조건부 쓰기 한 번). 변경 하나가 8 MiB까지 가므로 항목 크기 제한이 작은 DB는 큰 변경을 따로 둔다.
5. **한 문서의 연결은 한 서버 프로세스로 모은다.** 순서는 저장소가 지키지만, 변경을 다른 사람에게 바로 전하는 일은 프로세스 안에서 한다.
6. **자동 저장을 건다.** 변경 기록은 서버에 있지만 파일은 누가 저장해야 생긴다. 주기적으로 `doc.save()`를 부르거나 마지막 사람이 닫을 때 저장한다. 저장하는 사람은 저장 동안 입력이 잠깐 멈춘다.

## 알아 둘 동작

- **편집 묶음(epoch).** 처음 여는 사람의 파일이 기준이 되고, 그 위에 변경 기록이 쌓인다. 저장이 끝나고 아무도 없는 채 10분이 지나면 묶음이 끝나고, 다음에 여는 사람의 파일(마지막 저장본)로 새로 시작한다. 저장 안 된 변경이 있으면 묶음은 끝나지 않는다.
- **끊겼다 이어도 편집은 남는다.** 끊긴 동안 친 것은 다시 이으면 보낸다. 30초 안에 확정하지 못한 저장은 `offline`으로 거절되고 입력이 다시 열린다.
- **어긋나면 멈춘다.** 페이지들이 같은 판에서 문서 지문을 서버에 보내고, 다르면 모두 읽기 전용이 되며 묶음을 버린다. 마지막 저장 뒤의 편집은 잃는다. 틀린 파일을 저장하지 않으려고 일부러 그렇게 한다. 각 페이지는 화면 그대로를 내려받을 수 있다(`exportLocal`).
- **편집 형식을 바꾼 판을 배포할 때.** 어댑터의 `schema`가 다르면 옛 묶음에 들어갈 수 없다(`schema_mismatch`). 묶음이 끝나기를 기다리거나 `reset`한 뒤 배포한다.
- **시트 구조 변경 한도.** 한 묶음에서 행·열·병합·크기 변경 기록이 한도에 가까워지면 그 편집을 거절하고 "저장한 뒤 모두 닫고 잠시 뒤 다시 열어 달라"고 알린다.

## 확인한 것과 아닌 것

- 순서와 "정확히 한 번"은 TLA+ 모델 검사(`formal/collab-protocol/`)와 무작위 네트워크 시험으로 확인했다. 범위는 그 폴더의 `SCOPE.md`에 있다. 통과는 그 범위에서 반례가 없다는 뜻이다.
- 편집기별 수렴은 어댑터마다 무작위 적합성 시험과 브라우저 두 개 시험(`apps/web/tests/collab-*.spec.ts`)으로 확인했다.
- 확인하지 못한 것: 실제 네트워크와 여러 사람의 부하, 오래 가는 저장소 위에서의 동작, 사람 수가 많을 때 느린 쪽이 계속 밀리는 정도, 모바일 브라우저.
