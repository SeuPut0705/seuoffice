# 실시간 공동 편집

여러 사람이 같은 문서를 같은 순간에 고친다. 붙이는 쪽(호스트)이 `collab` 옵션으로 열 때만 켜진다. 옵션 없이 연 문서와 데스크톱 앱에서는 공동 편집 코드가 돌지 않는다. 다만 이 일을 하며 고친 것 가운데 데스크톱에도 적용되는 것이 있다(`upstream-edits.md`). 슬라이드 렌더러의 결함 넷(다시 그려져도 치던 글 유지, 보던 슬라이드를 순서가 아니라 슬라이드로 따라가기, 반영되지 않은 끌기 되돌려 그리기, 거절된 노트 쓰기의 초안 유지)과 PDF 저장(링크 주소와 날짜 입력란 형식에 괄호, `\`, ASCII 밖 글자가 있을 때 쓰는 방식)이다. 방향과 버린 대안은 [결정 0023](decisions/0023-실시간-공동-편집.md)에 있다.

> 시험 단계다. 실제 호스트, 오래 가는 저장소, 실제 네트워크에 붙여 쓴 적이 아직 없다. 어긋남을 감지하면 마지막 저장 뒤의 편집을 버리고 멈추는 것이 기본 동작이다. 실제 문서를 올리기 전에 아래 "실제로 쓰기 전에"를 먼저 한다.

## 한눈에

- 가운데 서버(`@seuoffice/collab/server`)가 편집 순서를 정한다. 문서마다 변경 기록 하나를 두고, 변경은 최신 판 위에서 만든 것일 때만 붙는다. 서버는 변경 내용을 읽지 않는다.
- 편집기 iframe 안의 엔진(`@seuoffice/collab/client`)이 "확정된 상태 + 아직 확정 안 된 내 편집"을 들고, 밀리면 내 편집을 남의 편집 위로 옮겨 다시 보낸다.
- 편집기마다 어댑터 하나가 "옮기는 방법"을 구현한다(`apps/<앱>/src/web/collab-*.ts`).
- 주소와 토큰은 붙이는 쪽 페이지가 가진다. iframe은 embed 통로로만 서버에 닿는다.

같은 것을 두 사람이 동시에 고치면 서버가 나중에 받은 쪽이 이긴다. 문서 본문만 글자 단위로 합쳐진다. 두 사람이 정확히 같은 자리에 같은 순간에 치면 두 사람의 글자가 한 글자씩 섞일 수 있다. 잃거나 두 번 들어가는 글자는 없다. 시트의 같은 셀, 슬라이드의 같은 글상자, PDF의 같은 주석은 한쪽 것만 남는다.

공동 편집 중에 달라지는 것이 더 있다.

- 시트: 남의 편집이 내 실행 취소가 건드릴 칸에 닿으면 내 실행 취소 기록을 비운다. 내 실행 취소가 남의 편집을 되돌리지 않게 하려는 것이다. 시트 크기는 엑셀 한도(1,048,576행, 16,384열)까지이고, 한 시트의 병합은 합쳐 1,048,576칸, 65,536개까지다. 넘는 편집은 안내와 함께 거절한다. 그래서 행이 끝까지 찬 시트에는 행을 넣을 수 없고, 병합이 아주 많은 시트에서 행·열을 한꺼번에 많이 넣는 편집도 거절될 수 있다.
- 문서: 화면에 HTML이나 주소로 들어가는 값이 규칙에 맞지 않는 편집(붙여 넣은 내용에 딸려 온 값 포함)은 안내와 함께 거절한다. 남이 보낸 편집에 거는 규칙을 내 편집에도 걸어야 두 사람의 파일이 같아진다. 링크는 http, https, mailto, tel, ftp, file과 문서 안 이동만 받는다.
- 슬라이드: 새 링크는 http, https, mailto만 넣을 수 있다. 글상자에 원래 있던 링크는 그대로 둔다. 그 밖의 새 주소는 글은 남기고 링크만 뺀다.
- PDF: 링크는 http, https, mailto만 넣을 수 있다. 날짜 입력란의 형식은 글자, 숫자, 빈칸, `. , : / -`만 64자까지 받는다.
- 암호 걸린 PDF는 암호를 넣은 뒤에야 `opened`가 온다. 붙이는 쪽은 `opened` 전에도 편집기 틀을 보이게 둔다.
- 한 묶음이 길어질수록 늦게 들어오는 사람은 변경 기록을 처음부터 따라가느라 오래 걸린다. 모두 저장하고 닫으면 다음에 새로 시작한다.

스트리밍으로 여는 큰 통합 문서와 어댑터가 없는 형식은 페이지가 `collab_unavailable`로 거절한다. 붙이는 쪽은 그때 `collab` 없이 잠금을 잡고 다시 연다.

## 붙이는 쪽이 할 일

### 화면

```ts
import { openDocument, SeuofficeEmbedError } from '@seuoffice/embed'

const collab = {
  // 처음 열 때와 다시 이을 때마다 불린다. 아직 열리지 않은 소켓을 돌려준다
  connect: async () => new WebSocket(await collabUrlWithTicket(docId)),
  onStatus: (status) => showPeers(status),
}

const doc = canEdit
  ? openDocument(container, {
      baseUrl,
      bytes, // 붙이는 쪽이 마지막으로 저장한 파일
      fileName,
      mode: 'edit',
      collab,
      onSave: async ({ bytes, fileName, version }) => {
        // 반드시: 이미 저장한 판보다 낮은 version은 throw로 거절한다
        await store.putIfNewer(docId, { bytes, fileName, version })
      },
    })
  : openDocument(container, { baseUrl, bytes, fileName, mode: 'view', collab })

try {
  await doc.opened
} catch (error) {
  if (error instanceof SeuofficeEmbedError && error.code === 'collab_unavailable') {
    doc.destroy()
    // 잠금을 잡고 collab 없이 다시 연다
  }
}
```

### 서버

```ts
import { WebSocketServer } from 'ws'
import { createCollabServer, memoryStore } from '@seuoffice/collab/server'

const collab = createCollabServer({ store: memoryStore() })

new WebSocketServer({ server, maxPayload: 50 * 1024 * 1024 }).on('connection', (ws, request) => {
  const principal = verifyTicket(request) // 붙이는 쪽의 인증: { documentId, userId, name, canEdit }
  if (!principal) return ws.close()
  collab.accept(serverSocket(ws), principal)
})
```

`serverSocket`(`ws` 소켓을 서버가 받는 모양으로 감싸는 열 줄)은 `packages/collab/README.md`에 있다.

### 꼭 지킬 것

1. **인증은 붙이는 쪽이 한다.** 서버는 `accept`에 넘어온 `Principal`을 믿는다. `canEdit: false`인 사람은 편집을 보낼 수 없다.
2. **낮은 판으로 덮어쓰지 않는다.** `onSave`가 받은 `version`이 저장해 둔 것보다 낮으면 throw한다. 지키지 않으면 늦게 도착한 옛 저장이 새 저장을 덮고, 다음 사람이 그 파일에서 시작해 그 사이 편집을 잃는다.
3. **공동 편집 밖에서 파일을 바꿨으면 `collab.reset(documentId)`를 부른다.** 새 판 올리기, 데스크톱에서 고친 파일 올리기가 그렇다.
4. **오래 가는 저장소는 붙이는 쪽이 만든다.** 실려 있는 것은 메모리 저장소(`memoryStore`)뿐이라 서버를 다시 띄우면 저장 안 된 편집이 사라진다. `CollabStore` 인터페이스를 자기 DB에 맞춰 구현한다. `append`는 원자적이어야 한다(조건부 쓰기 한 번). 변경 하나가 8 MiB까지 가므로 항목 크기 제한이 작은 DB는 큰 변경을 따로 둔다.
5. **한 문서의 연결은 한 서버 프로세스로 모은다.** 순서는 저장소가 지키지만, 변경을 다른 사람에게 바로 전하는 일은 프로세스 안에서 한다.
6. **자동 저장을 건다.** 변경 기록은 서버에 있지만 파일은 누가 저장해야 생긴다. 주기적으로 `doc.save()`를 부르거나 마지막 사람이 닫을 때 저장한다. 저장하는 사람은 저장 동안 입력이 잠깐 멈춘다.

## 알아 둘 동작

- **편집 묶음(epoch).** 처음 여는 사람의 파일이 기준이 되고, 그 위에 변경 기록이 쌓인다. 저장이 끝나고 아무도 없는 채 10분이 지나면 묶음이 끝나고, 다음에 여는 사람의 파일(마지막 저장본)로 새로 시작한다. 저장 안 된 변경이 있으면 묶음은 끝나지 않는다.
- **끊겼다 이어도 편집은 남는다.** 끊긴 동안 친 것은 다시 이으면 보낸다. 30초 안에 확정하지 못한 저장은 `offline`으로 거절되고 입력이 다시 열린다.
- **어긋나면 멈춘다.** 페이지들이 같은 판에서 문서 지문을 서버에 보내고, 다르면 모두 읽기 전용이 되며 묶음을 버린다. 마지막 저장 뒤의 편집은 잃는다. 틀린 파일을 저장하지 않으려고 일부러 그렇게 한다. 그때 각 사람은 `doc.exportLocal()`로 자기 화면 그대로의 파일을 받을 수 있다. 이 파일은 판 번호가 없으니 저장본을 자동으로 덮지 말고 사본으로 내려받게 한다.
- **편집 형식을 바꾼 판을 배포할 때.** 어댑터의 `schema`가 다르면 옛 묶음에 들어갈 수 없다(`schema_mismatch`). 묶음이 끝나기를 기다리거나 `reset`한 뒤 배포한다.
- **시트 구조 변경 한도.** 한 묶음에서 행·열·병합·크기 변경 기록이 한도에 가까워지면 그 편집을 거절하고 "저장한 뒤 모두 닫고 잠시 뒤 다시 열어 달라"고 알린다.

## 누구를 믿는가

- **편집 권한을 준 사람은 믿는다.** 서버는 변경 내용을 읽지 않으므로, 편집자는 문서를 마음대로 고칠 수 있는 것과 같은 수준으로 묶음도 망칠 수 있다. 고친 클라이언트로 틀린 지문이나 풀 수 없는 변경을 보내면 묶음이 `diverged`나 `adapter` 실패로 끝나고, 저장한 적 없이 "저장했다"고 알리면 10분 뒤 묶음이 끝난다. 어느 쪽이든 잃는 것은 마지막 저장 뒤의 편집이다. 그래서 자동 저장을 걸고, 편집 권한은 문서를 지울 권한을 줄 사람에게만 준다.
- **풀 수 없는 변경이 기록에 남으면** 그 묶음은 다시 열어도 같은 자리에서 실패한다. 복구는 각자 `exportLocal()`로 사본을 받고 붙이는 쪽이 `collab.reset(documentId)`를 부르는 것이다.
- **남의 화면에서 실행되는 것은 막는다.** 다른 편집자가 보낸 변경은 각 어댑터의 `decode`가 받는다. 아는 편집 종류와 크기·범위만 통과시키고, 화면에 HTML로 들어가는 값과 주소(수식 MathML, 링크, 그림)는 걸러낸다. 편집기 페이지의 CSP(`script-src 'self'`)가 그 뒤에 있다.
- **문서 보호와 작성자 이름은 편집자를 막지 못한다.** 편집 권한이 있는 사람이 고친 클라이언트를 쓰면 문서 보호·시트 잠금을 암호 없이 풀거나 잠긴 칸에 쓸 수 있고, 변경 추적·메모의 작성자 이름을 남의 이름으로 적을 수 있다. 서버가 변경 내용을 읽지 않기 때문이다. 보호가 꼭 지켜져야 하는 문서는 공동 편집으로 열지 말고 잠금으로 연다.
- **저장 파일을 다른 프로그램에서 열 때.** 받은 편집은 화면에 닿는 값을 거르지만, 문서 형식이 원래 허용하는 내용(예: 바깥 주소를 가리키는 필드)은 저장 파일에 들어갈 수 있다. 편집자가 직접 그런 파일을 올릴 수 있는 것과 같은 수준이다.
- **보기 전용 사용자는 변경도, 저장 알림도, 지문도 보낼 수 없다.**

## 실제로 쓰기 전에

이 판은 붙이는 쪽 없이 만든 첫 판이다. 실제 문서를 올리기 전에 붙이는 쪽에서 다음을 한다.

1. 자기 `CollabStore`를 만들고 `@seuoffice/collab/conformance`의 `storeContract`를 통과시킨다. 통과가 원자성을 증명하지는 않는다. 조건부 쓰기 한 번으로 구현했는지는 따로 본다.
2. 위 "꼭 지킬 것" 여섯 가지를 자기 서버에서 시험한다. 특히 낮은 판 거절과 자동 저장.
3. 사본 문서로 며칠 써 본다. 멈춤(`diverged`, `adapter`)이 나면 사본 내려받기(`exportLocal`) 단추가 보이는지, 다시 열 수 있는지 본다.
4. 문제가 생기면 `collab`을 빼고 잠금으로 여는 길을 남겨 둔다. 편집기 쪽은 그대로다.

## 확인한 것과 아닌 것

확인한 것.

- 순서와 "정확히 한 번": TLA+ 모델 검사(`formal/collab-protocol/`)와 무작위 네트워크 시험. 범위는 그 폴더의 `SCOPE.md`에 있고, 통과는 그 범위(클라이언트 둘·셋, 짧은 기록)에서 반례가 없다는 뜻이다.
- 편집기별 수렴: 어댑터마다 실제 편집기 모델을 머리 없는 환경에서 돌리는 무작위 적합성 시험.
- 브라우저 두 개(Chromium, 한 컴퓨터, 시험용 서버): 형식마다 서로의 편집이 보이고 어느 쪽이 저장해도 둘 다 든 파일이 나오는지(`apps/web/tests/collab-{docs,sheets,slides,pdf}.spec.ts`). 브라우저 시험이 실제로 넣는 편집은 좁다. 문서는 글자 입력, 시트는 셀 값과 행 넣기, 슬라이드는 글상자·노트·슬라이드 추가 삭제, PDF는 메모와 주석이다. 위 표의 나머지(문서의 표·그림·변경 추적·메모·각주, 시트의 서식·병합·시트 조작 등)는 머리 없는 시험만 거쳤다.
- 작업을 잃을 수 있는 여섯 장면을 형식마다(`collab-recovery-*.spec.ts`): 연결이 막힌 동안 입력, 입력 중 끊김(잃거나 두 번 들어간 것 없음), `diverged` 뒤 `exportLocal`, 오프라인 중 `exportLocal`, 늦게 온 옛 저장 거절, 연결 중 `reset`. hwp가 잠금 방식으로 열리는 것.
- 받은 편집을 거르는 경계는 독립 보안 검토를 두 번 받았다. 첫 검토에서 나온 우회(문서 HTML 주입 둘, PDF 저장 파일의 스크립트 액션, 시트 병합으로 멈춤)를 재현 시험과 함께 고쳤고, 두 번째 검토가 그 수정을 확인하며 더 찾은 것(시트 크기·병합 누적, 문서의 중첩된 단계 모양)과 고치는 중에 나온 것(PDF의 ASCII 밖 글자)도 고쳤다. 이 마지막 수정들은 다시 검토받지 않았다.

확인하지 못한 것.

- 실제 붙이는 쪽, 오래 가는 저장소, 실제 네트워크(지연, 프록시, 모바일 망), 여러 사람의 부하, 긴 묶음. 끊김은 시험 서버가 소켓을 끊는 방식으로만 만들었다.
- Chromium 밖의 브라우저(Safari, Firefox, 모바일).
- 큰 통합 문서가 `collab_unavailable`로 거절되는 경로는 시트의 실제 조건으로 시험하지 않았다(장난감 어댑터 시험만 있다). 30초 안에 확정하지 못한 저장의 `offline` 거절은 단위 시험만 있다.
- 실제 어긋남 감지. 브라우저 시험의 `diverged`는 시험 서버가 틀린 지문을 넣어 만든 것이라, 멈춤과 사본 받기는 보지만 두 편집기가 정말 달라졌을 때 잡는지는 머리 없는 시험만 본다.
- 시트 셀 편집기로 글 일부에만 서식을 준 편집이 상대에게 가는지는 머리 없는 시험만 했다.
- 경계가 정상 편집을 거절하는 경우. 만드는 동안 앱이 스스로 만드는 값이 세 번 걸렸다(PDF 선·화살표, 슬라이드의 기존 링크, 시트의 서식 있는 글). 셋은 고쳤지만 같은 종류가 더 없다는 확인은 없다. 걸리면 그 편집이 안내와 함께 거절된다.
- 보안 경계가 모든 화면 경로를 덮는지. 검토는 코드를 읽어 한 것이고, 문서의 표·차트 렌더러 일부와 슬라이드 캔버스 렌더러는 읽지 않았다.
- 데스크톱에 닿는 수정(슬라이드 렌더러 넷, PDF 저장)은 단위 시험과 CI의 데스크톱 e2e만 거친다. 다른 PDF 리더에서 저장 파일을 열어 보지 않았다.
